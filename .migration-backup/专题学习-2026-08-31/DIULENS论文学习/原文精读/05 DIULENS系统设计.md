# 4 DIULENS的设计
为了能够对集成到移动应用中的 CMP中的 DIU风险进行实际分析，我们开发了一个新的自动化框架，称为 DIULENS，其工作流程由四个步骤组成。图 3 提供了 DIULENS 的概述。第一步是数据收集，收集真实世界的移动应用、CMP 和第三方SDK进行分析。第二步涉及 CMP 和 SDK使用情况分析，通过静态和动态应用分析技术来识别 CMP 和 SDK的实际集成以及它们在应用内的动态使用跟踪。第三步是 LLM辅助的 CMP界面 分析，它调整 LLM 的使用以有效地发现 CMP界面。最后一步是 DIU风险检测，大语言模型通过 CMP界面 和 SDK使用信息进行推理，以实现通用 DIU风险检测。 DIULENS 的输出包括与违反 DIU规则（§ 3）相对应的已识别 DIU风险，以及违规原因的潜在归因。下面，我们介绍每个步骤，重点介绍有效 DIU风险分析所面临的挑战以及我们为应对这些挑战而设计的 CMP 目标。

### 4.1 数据收集
数据收集步骤构建了两套应用，一套适用于 Android，一套适用于 iOS，以及 CMP 及其涵盖的主要 SDK列表。
#### Android应用
为了收集 Android 应用，我们使用 Google Play Scraper [41] 来获取 54 个 Google Play 类别中每个类别中排名靠前的免费应用的包名称，例如健康与健身、教育、金融和工具。有了包名称，我们就可以使用为 APKPure [42]（Google Play 的替代应用商店 [43]）构建的自定义爬虫以 APK 或 XAPK 文件的形式下载应用代码。这个替代应用商店被认为是官方 Google Play 的镜像 [43]，并且由于缺乏对 Google Play 的 API 访问，通常被研究人员 [44]、[45] 用于获取应用代码。截至 2024 年 11 月，我们总共收集了每个 Google Play 类别中排名前 200 个应用的软件包名称，从而得出 10,588 个唯一的软件包名称。我们成功下载了 9,332 个独特应用的代码；其余应用在 APKPure 上不可用。
#### iOS应用
我们从流行的 App Store 分析平台 Appfigures [46] 获取了顶级免费 iOS 应用及其应用 ID 的列表。对于每个应用，我们使用 IPATool [47] 下载其代码 (IPA)。然后，我们使用 libimobiledevice 工具包 [48] 在 iPhone 上安装应用，并使用 Frida iOS dump [49] 解密它们。我们保留原始IPA文件和解密后的IPA文件，使用前者进行动态分析，后者进行静态分析。同样是在 2024 年底，我们成功获取了 3,496 个 iOS 应用。 CMP。我们收集了以下 CMP：(1) 已通过 IAB Europe 的合规性检查（或认证），以及 (2) 具有可供应用开发者使用的移动 SDK。具体来说，我们首先收集“TCF v2.2 CMP服务（移动）”[50] 的 CMP 列表中出现的 CMP。然后，我们通过手动探索 CMP的官方网站来验证移动 SDK的存在。截至2024年，已有53个CMP列入CMP列表（移动），其中21个已确认已发布移动SDK，其中21个支持Android平台，19个支持iOS平台。对于 21 个 CMP中的每一个，我们收集了其网站、软件包名称（适用于 Android）和框架名称（适用于 iOS，如果平台受支持）。 SDK。 CMP 有助于收集用户对各种第三方SDK的同意。为了实现全面的 SDK 覆盖，我们从几个著名的 SDK 注册服务机构收集了 SDK 名称及其元数据（例如网站、包名称和服务类型）：(1) IAB 全球供应商列表 [51]、(2) Google 广告技术提供商 (ATP) [52] 和 (3) Google Play SDK 索引 [53]。这些来源涵盖了各种服务类型的广泛 SDK，例如通常嵌入到移动应用中的广告、分析和实用程序。
请注意，ATP 和 Google Play SDK Index 发布的 SDK 并不限于 Android 平台，因为许多 SDK，尤其是最流行的 SDK，往往涵盖多个平台。我们总共收集了 1,858 个独特 SDK的信息。
### 4.2 CMP与SDK使用分析
#### 检测应用中的CMP与SDK集成
我们进行静态应用分析，以确定 CMP 和 SDK 是否集成到应用中。具体来说，对于Android应用，我们使用Soot [54]对代码进行反编译和转换，然后分析应用中包含的包。我们通过检测 CMP 和 SDK的包名称是否出现在应用代码中来检查它们是否存在。对于 iOS 应用，我们解压其 IPA 文件并遍历 Payload 目录来识别框架（.framework 文件）或动态库（.dylib 文件），它们对应于 CocoaPods、SPM 和 Carthage 等领先包管理器通常支持的动态链接 SDK。我们通过验证应用使用的框架是否包含 CMP的框架名称来检查 CMP 是否存在。在不太常见的情况下，iOS 应用可以通过静态链接集成 SDK。为了适应这种情况，我们在 iOS 应用二进制文件（Payload/<应用名称>.app/<应用名称> 处的 Mach-O 文件）上使用 otool [55] 来提取符号并检查 SDK 名称是否存在。此步骤通过检查代码的外观来报告集成到应用中的 CMP 和 SDK的列表。此类信息将（1）帮助 DIULENS 将分析范围缩小到集成CMP的应用，（2）为 CMP界面 上的 SDK 披露信息提供参考，以检测 DIU风险。
#### 分析SDK与CMP的动态使用轨迹
对于同时包含 CMP 和 SDK 代码的应用，我们会进行动态分析，以了解这些 CMP 和 SDK 在运行时的使用方式，特别是在个人数据访问和用户同意管理方面。为此，我们执行流量和 UI 分析。具体来说，我们首先收集一个 API 列表，这些 API 可以从几个开源隐私工具访问个人数据，例如 Android 的 Camille [56] 和 PrivacySentry [57]，以及 iOS 的 Lalaine [58]。该列表包括 12 个类别的 73 个 Android API，例如位置数据访问和设备标识符，以及 5 个类别的 140 个 iOS API，例如访问照片和联系人。当应用通过 UI 交互执行时（第 4.3 节），我们使用 Frida 挂钩这些 API 并记录每次调用的堆栈跟踪。我们匹配堆栈跟踪帧中的包名称或框架名称，以确定个人数据访问是否源自 SDK 代码。同时，我们确定在应用执行期间何时向用户显示 CMP界面（如第 4.3 节中详述）。此步骤的输出是一系列带有时间戳的事件，包括个人数据处理和 CMP界面 的显示。
### 4.3 LLM辅助的CMP界面分析
在本节中，我们将介绍 CMP界面 分析技术，其特点是有针对性的设计，以确保效率和全面的 GUI 发现。
#### 感知CMP指南的CMP界面判定
确定应用 GUI 是否与隐私相关的典型方法涉及分析隐私相关内容，例如使用“隐私”、“cookie”和“数据保护”等关键字检测隐私对话框[8]、[10]。然而，正如第 5.1 节中所评估的，这些方法无法可靠地识别 CMP界面。虽然与隐私相关的关键字也可能出现在 CMP界面 中，但仅靠它们是不够的，因为应用开发者实现的许多其他 GUI（例如隐私政策页面和非 CMP 隐私对话框）也包含这些关键字。我们的观察是，CMP 通常根据隐私相关框架（例如 TCF 政策 [35]）指定的高级指南（或要求）来实施 GUI。然而，CMP界面 的详细布局和内容可能因不同的 CMP 提供商而异，甚至在应用开发者之间也会有所不同，因为 CMP 通常是可配置的（如第 6 节中所示）。因此，确定 CMP界面 需要一种了解 CMP指南的方法，重点关注指南中描述的 CMP界面 的性质，而不是特定的 UI 内容（例如与隐私相关的关键字）。受此启发，我们设计了一种基于大语言模型的方法，其中应用 UI 由大语言模型评估，以确定其与 CMP的相关性。具体来说，我们使用 Appium [59]（一种跨 Android 和 iOS 平台自动化移动应用的开源工具）来推动应用 UI 的探索并提取 UI 信息。对于每个应用 UI，我们首先从 Appium 提供的页面源（中间布局文件）中提取所有 UI 元素，包括它们的属性，如名称、标签、坐标、大小等。接下来，我们将这些 UI 元素以及总结 CMP界面 性质的提示一起输入到 LLM 中，以评估 UI 是否符合 CMP界面 的资格。
图 9（附录）说明了源自 TCF 政策 [35] 和 ICC 指南 [21] 中概述的用户界面要求的提示。评估结果（第 5.1 节详述）证实，与基于关键字的方法 [8] 相比，该方法在确定 CMP界面 方面实现了高覆盖率 (84.8%) 和精度 (100.0%)，而基于关键字的方法的覆盖率为 55.9%，精度为 37.9%。
#### LLM引导的CMP导航路径发现
显示 CMP界面 的一般建议是在应用启动时显示它们，以确保隐私合规性 [60]，例如，在收集任何个人数据之前获得同意。然而，根据隐私法规 [27] 和 TCF 政策 [35] 等行业标准的要求，应用必须重新显示 CMP界面，以允许用户撤回同意。重新显示 GUI 的导航流（或路径）未定义，并且通常在不同的应用中有所不同，具体取决于特定的应用 UI 设计。在应用中发现这些 CMP界面 并非易事，但对于全面分析至关重要。然而，大多数公开的 UI 练习器都是覆盖率驱动的 [61]、[62]、[63]、[64]，其主要目标是增加应用测试覆盖率，而不是专门针对特定类型 GUI 的发现。为了弥补这一差距，我们设计了一个 LLM 引导的 GUI 练习器，旨在有效发现 CMP的导航流。该练习器由两个关键组件组成：(1) 通向已知 CMP界面 的导航流程的先验知识，以及 (2) 指导 GUI 探索优先级的提示。具体来说，我们首先通过审查集成CMP的 24 个应用（选自 5 个 CMP 网站上列出的合作伙伴或客户，但未包含在我们的移动应用数据集中）来构建先验知识，并确定了通往 CMP界面 的 11 个导航流。每个流程都用与用户与 GUI 交互相对应的文本标签列表进行描述（例如，在导航流程中单击的按钮标签）。接下来，我们制作了一个提示（如附录中的图 10 所示），它将通向当前 GUI 的导航流程、GUI 上的所有可点击元素（由 Appium 提取）以及先验知识作为输入。
然后，提示会生成一个输出，根据将导航流程推进到更接近 CMP界面 的可能性，对可点击元素进行排名。 Appium 可以根据有序元素与当前 GUI 进行交互。在此提示下，导航流的探索很大程度上遵循深度优先的搜索策略，由 CMP 特定知识驱动。当新的 CMP界面 出现时，探索过程终止；一旦应用从 CMP界面 导航到非 CMP界面，探索过程就会重新启动。当所有应用 GUI 都已探索完毕或达到时间限制时（这是移动应用分析中的常见做法 [65]），探索结束。我们在第 5.1 节中的评估证明了这种 LLM 引导的发现过程相对于最先进的 GUI 探索方法具有显着优势。
#### CMP内部图形用户界面探索
与应用开发者开发的同意对话框（通常由交互有限的简单单页 GUI 组成）不同，CMP 具有更复杂的 GUI 结构，通常涉及多个互连的屏幕。分析 CMP 需要彻底探索所有 CMP界面 及其内部的交互。发出随机 UI 事件 [66] 是一个潜在的解决方案，因为它确保了 UI 的广泛覆盖。然而，一个重大挑战阻碍了该方法在 CMP 内导航时的有效应用。 CMP界面 通常包含“接受”或“拒绝”选项等元素，与这些选项交互时，可能会导致探索因导航离开当前 CMP 而提前结束。为了解决这个问题并确保 CMP界面 探索的效率和覆盖范围，我们开发了两种管理 CMP 内 GUI 交互的策略。第一个是延迟交互策略，我们将与 CMP 退出选项的交互延迟到最晚的可能时刻。为了实现这一点，我们根据对前 10 个 CMP 文档的手动分析，手动编制了与可能导致 CMP 退出的 UI 元素相关的八个关键字（即接受、批准、允许、拒绝、拒绝、保存、确认、关闭）的列表 [37]。对于 CMP中的每个 GUI，我们识别包含这些关键字的 GUI 元素，并保留与它们的交互，直到探索结束。第二个是记录和重放策略。具体来说，对于每个 GUI，我们通过对 Appium 中同时具有非空名称和标签属性的静态 GUI 元素的组合进行哈希处理来生成 GUI 指纹。
然后，我们在运行时将每个导航路径记录为一系列 GUI 指纹，其中每个指纹与一系列 GUI 内事件相关联，例如对可点击元素的点击、滚动操作以及垂直滚动量。如果退出前尚未完全探索 CMP，Appium 脚本将根据记录的导航路径重播 GUI 交互，并恢复与其余 GUI 元素的交互。这些组合策略实现了 CMP界面 的高效率和覆盖率，总体 CMP界面 覆盖率达到 84.8%，与随机点击相比，在相同的时间内识别出更多的 GUI，而随机点击通常会导致 CMP界面 异常退出。
### 4.4 DIU风险检测
由于 CMP实现的多样性及其在移动应用中的使用不一致，使用高级 DIU规则（§ 3）检测违规行为提出了实际挑战。例如，Koch 等人的先前工作。 [8] 依赖于基于规则的系统，使用正则表达式和硬编码启发式来检测同意对话框违规行为。虽然对网站上使用的 CMP 进行大规模分析非常有效，但他们的方法缺乏灵活性，并且通常无法在移动应用中的不同 CMP界面 之间进行推广。因此，有效检测 DIU风险需要一种新方法，根据规则稳健评估 CMP界面 和 SDK使用情况，同时确保捕获这些违规行为的各种表现形式的普遍性。为了满足这一需求，我们提出了一种基于大语言模型的 DIU风险检测方法，利用大语言模型对与规则相关的 GUI 进行语义推理的能力所引入的通用性。您是识别移动应用内同意管理平台（CMP） GUI 问题的专家。您将获得以下信息： - CMP界面 屏幕截图：CMP界面 屏幕截图的 URL 列表，其中包含指示 GUI 何时显示的时间戳。例如， [("https://a.com/1st_layer .png", "2025-02-12T14:30:00"), ("https://a.com/2 nd_layer.png", "2025-02-12T14:31:00")] 表示两个 GUI 屏幕截图。 - CMP界面 导航流：UI 导航事件列表，每个事件包括源 GUI、目标 GUI 和触发操作。例如，两个 CMP 层之间的导航：[("1st_layer.png", "2nd_layer.png", "click '管理选项'按钮")]。 - SDK使用数据：列出 SDK数量、名称和服务类型的句子。
例如：这个应用使用了50个第三方SDK，包括Adjust（分析），...，以及<忽略以减少空间>。 - SDK数据访问事件：由 SDK 发起的一系列数据访问事件，带有指示事件发生时间的时间戳，例如 [(“2025-02-12T14:29:30Z”、“AppLovin”、“访问设备标识符”)]。使用上述信息，检查是否违反以下规则： <带有示例性示例的 DIU规则。> 请注意： - 您应该根据每条规则评估 CMP界面、导航流程、SDK使用数据和数据访问事件。 - 对于每个应用，您的回答应根据规则编号，以“是”（违规）或“否”（无违规）开头，如果是“是”，则后跟一句话描述。 - 对于低可信度违规行为，请勿报告“是”。

#### 融合CMP与SDK使用数据的LLM提示词
该方法的核心是 LLM提示，它描述了应用的 CMP界面 和 SDK使用信息，有效地使移动应用代码适合基于 LLM 的分析。如图 4 所示，提示首先定义 LLM 在分析 CMP界面 中的角色、指定输入格式、列出检测规则并概述预期的输出格式。我们设计输入以涵盖不同的视角，包括单个 CMP界面、跨不同 GUI 或 SDK使用和 CMP界面 之间。具体来说，输入包括第 4.3 节中提取的 CMP界面 屏幕截图列表。这些屏幕截图标有在 CMP界面 分析期间出现的时间戳，并且大语言模型可以通过指向存储在 Dropbox 中的图像的 URL 来访问这些屏幕截图 [67]。我们还为大语言模型提供通往每个 CMP界面 的导航流程，以前面的 GUI 列表以及触发下一个 GUI 显示的相应 GUI 交互的形式。该提示还包括 SDK使用信息，例如所使用的 SDK的数量和列表、其服务类型，以及由 SDK 发起的带时间戳的数据访问事件序列。输入中包含 CMP界面、GUI 导航流（通过 CMP界面 分析识别，第 4.3 节）和 SDK使用数据（通过静态和动态应用分析收集，第 4.2 节），提示将能够通过一组可扩展的 LLM 推理规则检测 DIU风险（我们将在后面说明）。
#### 检测DIU风险的推理规则
我们根据§ 3中概述的DIU规则设计了用于检测DIU风险的LLM推理规则。具体来说，对于DIU规则1，LLM将SDK使用信息中的数据访问事件的时间戳与CMP界面屏幕截图的时间戳进行比较，以确定是否有任何SDK在获得用户同意之前访问用户个人数据。 DIU规则 2 的推理规则会比较 SDK使用信息和 CMP界面 屏幕截图，以识别 CMP界面 中 SDK 相对于应用实际使用的 SDK 过度披露和不足披露的情况。它还检查跨 CMP界面 的 SDK 披露，以识别 SDK信息中的任何不一致之处。 DIU规则 3 的推理规则侧重于检查应用是否允许用户通过重新显示 CMP界面（特别是通过易于访问的路径）来撤回同意。此外，该规则还将检查 CMP界面 是否允许用户自由设置非严格必要的 SDK 和数据处理目的的同意状态，以及当前 CMP界面 是否允许用户明确确认其更改（例如，通过保存按钮）。最后，DIU规则 4 的推理规则检查各个 CMP界面 及其导航路径，以确定：(1) 任何用户操作（例如按钮单击）是否可能导致误导性的同意状态，以及 (2) 沿导航路径跨 GUI 的任何用户交互是否在视觉上或语义上具有误导性。图 4 中的规则部分提供了推理规则的摘要。
#### DIU风险归因
DIU风险可能来自各个利益相关者，包括实施 CMP的 CMP 开发人员、将 CMP 集成到其应用中的应用开发者，或有时两者兼而有之。对于报告的每个 DIU风险，我们都会尽最大努力通过跨应用分析来识别潜在来源。直观上，我们可以根据应用使用的 CMP 对应用进行分组。对于使用相同 CMP的每组应用，如果所有应用报告相同的 DIU风险，则 DIU风险可归因于 CMP 开发者；否则，将归咎于应用开发者。然而，在实践中，应用开发者可以决定显示哪些 CMP界面 [15]，从而导致一些 DIU风险（即使它们是由 CMP 开发人员引起的）出现在某些应用中，而不会出现在其他应用中。为了补充这一点，我们不仅根据 CMP 名称，还根据应用中显示的 CMP界面 数量进一步细化应用分组。应用开发者的DIU风险主要是由于CMP集成过程中的错误配置造成的。为了进一步调查这些错误配置的潜在原因，我们审查了集成过程，以确定可能使正确配置变得困难的任何与 CMP 相关的因素。 § 6 报告了本研究中确定的 DIU风险及其对应用和 SDK 开发人员的归因。
