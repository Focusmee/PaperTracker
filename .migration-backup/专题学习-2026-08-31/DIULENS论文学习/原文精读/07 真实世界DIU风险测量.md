#### 应用对CMP的使用情况
我们在 9,332 个 Android 应用和 3,496 个 iOS 应用上运行 DIULENS，以识别那些使用 CMP的应用，每个应用的平均 LLM 查询成本约为 0.01 美元。通过静态应用分析（第 4.2 节），我们发现 675 个（7.2%）Android 应用和 159 个（4.5%）iOS 应用集成了至少一个 CMP。 iOS 应用中 CMP的集成率低于 Android 应用，我们认为这与苹果应用跟踪透明度（ATT）框架的引入有关[73]。自 iOS 14.5 起，iOS 上的应用需要通过 ATT 框架请求用户同意，专门用于通过设备的 IDFA 跟踪用户。集成 ATT 框架和 CMP 可能会导致应用两次请求类似的同意，从而可能导致令人困惑和令人沮丧的用户体验 [74]。此外，这种情况也让开发人员感到困惑，事实表明，即使是 Google UMP 等领先的 CMP 平台，在 ATT 已经实施的情况下，也曾就是否有必要使用 CMP 提供过含糊不清的指导 [75]。鉴于此，我们怀疑一些 iOS 应用开发者可能由于 ATT 的存在而选择不集成CMP。然而，值得注意的是，ATT 并不否定用户同意数据处理的要求（使用个人数据用于跟踪目的除外），并且无意取代 CMP [74]、[76]。因此，可能需要更多的工程和研究关注来更好地将 CMP（用于遵守隐私法规）与 ATT（用于 iOS 平台上的合规性）结合起来，以确保与用户同意相关的真正的隐私合规性。
| 发现1：由于苹果 ATT 框架的实施，iOS 应用集成的 CMP 往往比 Android 应用少，这凸显了需要更好地集成CMP 与 ATT，以确保符合平台级要求和隐私法规。这些集成CMP的应用是最受欢迎的，在 Android 上平均下载量为 2,865 万次，在 iOS 1 上有超过 165,000 条评论。DIULENS 进一步在 546 个 Android 应用和 110 个 iOS 应用中识别出了 CMP界面，而在其他应用中没有识别出 CMP界面。我们观察到 37 个 Android 应用的 CMP界面 分析不成功，原因如下：19 个应用无法从我们位于挪威的测试位置执行，10 个应用与测试设备不兼容，其余 8 个应用要么要求用户下载不可用的资源（例如游戏资产），要么被付费墙阻止，从而阻止了真实应用 GUI 的渲染。同样，由于 iPhone 上安装的困难（15 个应用）、Appium 分析 GUI 和执行交互的能力有限（10 个应用）以及在我们的评估期间从 App Store 中删除了一些应用（3 个应用），CMP界面 分析对 28 个 iOS 应用不成功。检测到的 DIU风险概述。在这些应用中，有 371 个 Android 应用（546 个应用中的 67.9%）和 26 个 iOS 应用（110 个应用中的 23.6%）被报告违反了至少一项 DIU规则。违反最多的规则是 DIU规则 2（CMP界面 上披露信息的可信度），占 Android 上 DIU风险的 46.9% 和 iOS 上 DIU风险的 17.3%。 iOS 上较低的 DIU风险率可能归因于采用了更简化的 CMP界面 设计。 |

### 6.2 违反DIU规则1的风险
50 个应用 (7.6%) 包含第三方SDK，这些第三方SDK 在显示 CMP界面 之前开始收集个人数据，违反了 DIU规则 1（CMP界面 的计时）。出现这种情况是因为应用开发者经常在加载 CMP 之前错误地初始化一个或多个 SDK。此外，尽管所有应用都在欧盟（GDPR 适用的地区）内进行了测试，但仍发现 12 个应用显示为 CCPA [24] 设计的 CMP界面，旨在保护加州居民。具体来说，这些应用不会在数据收集开始之前（例如，在应用启动时）请求同意，而是假定默认情况下允许数据收集，并且仅在隐私设置中显示 CMP界面，以便为用户提供退出选项。进一步的分析表明，这些应用虽然也为欧盟居民提供服务，但始终通过硬编码设置 ID 呈现与 CCPA 相关的 GUI，这表明开发人员可能误解了适用的隐私法规。
#### Flip Master案例
是一个使用 Usercentrics CMP的真实示例。该应用直接启动进入游戏，无需预先显示任何 CMP界面。用户只能通过导航到“设置 - 隐私设置”来访问 CMP界面，在那里他们会发现默认情况下打开的“定向广告”选项。此设置意味着只要用户与应用互动，应用就假定用户同意 SDK数据收集。应用中包含 CMP界面 的目的只是为了让用户选择退出，而不是征得他们的同意。
| 发现3：7.6% 集成CMP的应用在收集用户同意之前访问个人数据，因为应用开发者未能 (1) 正确协调 CMP 和 SDK的执行顺序，以及 (2) 配置 CMP 以遵守适用的隐私法规。 |

### 6.3 违反DIU规则2的风险
总共有 256 个 (46.9%) Android 应用和 19 个 (17.3%) iOS 应用被报告因不可信（不准确或不正确）的 SDK 披露而存在 DIU风险。这些DIU风险主要体现在两个方面：（1）CMP界面上的SDK披露与SDK使用不一致；（2）不同CMP界面之间的SDK披露不一致。 (a) 在 9GAG 应用中请求同意过多的 SDK (b) 在 Animal Hunter 应用中将营销 SDK 标记为“必需”

#### SDK披露与实际使用不一致
所有分析的应用中，有 214 个（32.6%）存在 DIU风险，因为 CMP 请求用户同意的 SDK 与应用实际使用的 SDK 不匹配。这些 DIU风险中的绝大多数表现为过度披露 (95.4%)，即 CMP界面 寻求同意的 SDK数量多于集成的 SDK，而少数风险则是披露不足的情况 (4.6%)，即 CMP界面 中提供的 SDK数量少于实际使用的数量。前者未能提供具体且知情的同意请求，通过不必要的长SDK列表压倒用户，导致决策疲劳，并使他们面临不必要的隐私风险[78]，而后者由于缺乏对特定SDK处理数据的同意而导致直接隐私侵犯[27]，[39]。过度披露的一个例子是 9GAG 应用，该应用的安装量超过 4400 万次。尽管仅使用 76 个 SDK，但 OneTrust [79] 提供的 CMP界面 请求同意多达 865 个 SDK（如图 5a 所示）。此问题源于以下事实：OneTrust 默认情况下包含 IAB Vendor 2.2 框架 [11] 中的所有供应商，并要求应用开发者根据应用中实际使用的 SDK 主动检查和配置供应商列表。然而，9GAG应用的开发者采用了默认设置，而没有根据应用的实际SDK使用情况进行定制。 Clock Launcher 就是一个未充分披露的例子，它是一款使用 Iubenda 作为 CMP的闹钟和启动器应用 [80]。 Iubenda 提供的 GUI 请求同意空的 SDK列表，而该应用实际上集成了第三方SDK，例如 Google Mobile Ads SDK 和 Adjust SDK，这两个 SDK 都处理个人数据（如 IAB 供应商列表 [51] 中所述）。
我们对其他受影响应用的分析揭示了类似的原因：应用开发者要么接受默认的 CMP配置，而不根据其应用进行定制（与行为研究中观察到的默认效果偏差一致，即用户倾向于坚持默认设置 [81]、[82]），要么在自定义 CMP 时省略 SDK（尽管目前尚不清楚这些遗漏是意外还是故意）。
| 发现4：近三分之一集成CMP的应用披露了与实际 SDK使用情况不符的不可信 SDK信息。由于应用开发者在集成CMP 时未能正确配置 SDK列表，因此绝大多数此类应用都会请求用户同意使用过多的 SDK。除了 214 个应用的 SDK信息不一致之外，我们还发现 165 个应用未在其 CMP界面 上披露 SDK信息。具体来说，这些应用将 CMP配置为仅显示 SDK类别（类似于附录中的图 8），同时对用户隐藏详细的 SDK列表（如我们之前在第 6.1 节中所述）。这种做法不符合 TCF 政策 [35]，该政策要求 CMP界面 提供有关“指定第三方列表”的信息，也不符合 GDPR 第 13 条 [77] 等隐私法规，该法规要求数据控制者身份的透明度。然而，我们从报告中排除了这 214 个应用，因为它们没有明确披露 CMP界面 上不可信的 SDK信息，而是代表了根本没有披露 SDK的特殊情况。 |
| --- |
#### 不同CMP界面之间的SDK披露不一致
总共有 61 个应用 (9.3%) 被发现在 CMP 用户界面内部或之间包含不一致的信息。一个突出的例子涉及 50 个应用，全部由 Voodoo [83] 开发，它们集成了 SourcePoint 作为其 CMP。在最初的 CMP界面 中，这些应用通知用户他们与 36 个合作伙伴（即 SDK）合作。但是，单击“查看所有提供程序”按钮后，用户将看到另一个 GUI，其中包括文本视图和列表视图。虽然文本视图仍然指出使用了 36 个合作伙伴，但列表视图显示了 70 个 SDK。这种 DIU风险给用户带来了错误的印象，即应用依赖的第三方SDK 比实际少得多。我们向 Voodoo 报告了这个问题，后者确认差异是由于“文本与合作伙伴计数模块之间取消集成导致的链接问题”造成的，并已解决该问题。此问题影响了我们数据集中集成 SourcePoint 的所有 57 个应用。此外，我们发现四个使用其他 CMP的应用（例如 iubenda 和 OneTrust）似乎故意操纵公开的 SDK数量，进一步加剧了用户的误解。
| 发现5：某些 CMP中的实施缺陷以及应用开发者故意操纵 SDK 披露信息，导致 CMP界面 之间的 SDK信息不一致。 |

### 6.4 违反DIU规则3的风险
据报告，共有 90 个 (16.5%) Android 应用和 8 个 (7.3%) iOS 应用存在违反 DIU规则 3（可撤回和非强制用户同意）的 DIU风险。
#### 不可撤回的用户同意
根据主要隐私法规的规定[24]、[27]、[39]，用户应该能够像给予同意一样轻松地撤回同意。 TCF 实施指南 [35] 进一步要求应用开发者（即发布商）提供允许用户撤回同意的可访问设置。然而，运行 DIU风险显示，15 个 (2.5%) 应用不包含任何允许用户在给予同意后修改其同意的 GUI。例如，C-SPAN Now（一款使用 OneTrust CMP的新闻应用）仅在应用初始启动期间提供同意选项。应用运行后，用户无法重新访问或调整他们的同意偏好。应用的设置中完全没有撤回同意的选项，这实际上迫使用户要么永久接受其最初的决定，要么卸载并重新安装应用以重置他们的首选项。
| 发现6：2.5% 的应用未能提供可访问的 CMP界面 供用户撤回同意。 |
| --- |
#### 受强迫的用户同意
共有 90 个应用 (13.7%) 被发现强迫用户提供同意，原因要么是应用开发者的做法，要么是 CMP实现中的缺陷。强制用户同意的主要原因是应用开发者未能（以及潜在的操纵）对 SDK进行分类，即在 CMP配置中设置 SDK类别。以使用 Usercentrics CMP的 Animal Hunter 应用为例。除了来自 IAB 供应商列表 [51] 和 Google 广告技术提供商 [52] 的 SDK（两者本质上都集成到 Usercentrics 中）之外，CMP 还允许应用开发者手动添加不属于这些列表的 SDK。开发人员可以指定每个 SDK的名称、描述，以及最重要的类别，例如 Essential、Marketing 或 Function。值得注意的是，标记为“Essential”的 SDK 被视为严格要求的，因此不受同意请求的约束，即默认情况下，用户被视为已授予同意，无法修改此设置。我们观察到，Animal Hunter 应用利用了这一 CMP 功能，该功能旨在支持更广泛的 SDK，将 AppLovin 和 Facebook SDK 等营销 SDK 标记为 Essential（如图 5b 所示），从而迫使用户同意其使用，而无法选择退出。在 78 个应用中发现了类似的 DIU风险，但外观略有不同。例如，另一个 CMP OneTrust 将 SDK 分为五个 cookie 类别：绝对必要、性能、功能、目标和社交媒体。默认情况下，只有 Strictly Necessary cookie（及其关联的 SDK）被标记为“始终处于活动状态”，以防止用户拒绝它们。
然而，OneTrust 允许应用开发者将任何 cookie 类别配置为“始终处于活动状态”，从而有效地强制用户同意非必要的 SDK。 45 个应用（例如 Forever 21）被发现利用了上述配置。我们无法查明此类开发人员行为的明确原因，无论是技术故障还是故意操纵。但对研究文献的回顾表明，一些开发人员的做法可能源于

| 发现7：一些领先的 CMP 允许开发人员指定哪些 SDK 是必需的，从而假定他们同意，而不向用户提供选择。有证据表明，应用开发者确实有意或无意地利用了此功能来绕过营销 SDK的用户同意。强迫用户同意的另一个原因在于 CMP实现中的缺陷。具体来说，我们发现 56 个应用 (8.5%) 在初始 CMP界面 上包含指向“合作伙伴（供应商）列表”的链接。但是，当用户导航到列表并尝试修改其对某些合作伙伴（即 SDK）的同意首选项时，没有明确的选项来保存更改（例如“保存”或“确认我的选择”按钮），也不会自动保存更改。因此，无论之前的用户选择如何，重新输入合作伙伴列表始终会显示已授予同意。这种 DIU风险可能会误导用户相信他们的同意偏好已被记录，而实际上这些偏好尚未生效。对这些应用的仔细分析表明，它们都使用 OneTrust 作为 CMP。图 7（在附录中）显示了 OneTrust 提供的初始 GUI 和供应商列表。我们向 OneTrust 报告了此问题，他们目前正在调查该问题。 |

### 6.5 违反DIU规则4的风险
总共有 30 个应用 (4.6%) 被发现具有支持用户交互的 CMP界面，导致对用户同意选择产生模糊影响，可能违反了必须通过明确的肯定性操作获得用户同意的要求 [27]、[39]、[85]。 CMP 事实上的标准实现是提供内置 GUI，允许用户对第三方SDK 做出肯定操作，例如“接受全部”或“管理设置”。然而，七个 CMP 被发现允许应用开发者自由定制这些操作的外观，为滥用和同意操纵打开了大门 [36]，[86]。一个例子是使用 Usercentrics CMP的 Animal Hunter 应用。该应用被发现用“Tap to Play”和“Details”取代了两个标准选项，其中“Tap to Play”表明点击它会进入主要游戏内容。但实际上，单击此选项会立即表示同意使用所有 SDK，但所有用户可能不会立即清楚这一事实。应用开发者所做的自定义各不相同，例如，将“全部接受”替换为“确定”、“是”或“继续”。这种定制是否真的会导致隐私侵犯是有争议的，但根据之前对用户隐私认知的研究[15]，它们确实可能会在用户做出同意选择时造成混乱或误导。
| 发现9：应用开发者可以自行决定自定义 CMP界面 元素（例如按钮）的外观，这可能会在用户做出同意选择时造成混乱或误导。歧义不仅发生在单个 CMP界面 上，而且还体现在多个 CMP界面 之间的导航路径中，在 47 个 (7.2%) 应用中发现了这种情况。分析显示，所有这些应用都使用 OneTrust 作为其 CMP。值得注意的是，我们观察到这些应用在 CMP界面 中将某些数据处理目的（例如，“匹配并合并来自其他数据源的数据”）列为“始终处于活动状态”，这表明用户不能拒绝这些目的。但是，当用户单击这些目的时，他们会被重定向到另一个 CMP界面，该 GUI 会显示 SDK列表，其中包含切换选项，以同意或拒绝将其用于这些目的。这会产生差异，因为最初的 CMP界面 会导致用户相信该目的无法被拒绝，而后续的 GUI 则允许他们拒绝该目的，从而给应用用户带来混乱和模糊的体验。图 6 显示了此 DIU风险涉及的两个 CMP界面。我们已向 OneTrust 报告此问题，该公司目前正在调查此问题。 |
