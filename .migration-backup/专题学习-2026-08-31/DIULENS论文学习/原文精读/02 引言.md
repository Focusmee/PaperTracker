# 1 引言
随着移动应用日益渗透到日常生活中，它们也带来了重大的隐私风险。例如，仅在 2024 年，谷歌就屏蔽了 130 万个因过度访问个人数据的应用 [1]，而在 2022 年，苹果公司标记了近 40 万个应用在用户不知情的情况下收集用户数据 [2]。这些风险不仅源于应用开发者编写的代码，而且在很大程度上还源于将各种第三方SDK（或库）集成到应用的供应链中[3]、[4]。由于这些 SDK 带来的复杂性，有效管理它们并确保一致和集体遵守主要隐私法规成为一项重大挑战。例如，GDPR [5] 和 COPPA [6] 要求包含 SDK的应用在任何 SDK 收集或处理个人数据之前获得有效的用户同意，并且该同意满足关键的有效性标准，例如知情、自由给予、具体和明确。然而，由于缺乏有效的机制来管理 SDK的同意状态，目前移动应用中的 SDK集成经常被报道违反这些标准 [7]、[8]、[9]、[10]，从而带来法律合规风险。为此，一种行业解决方案是开发同意管理平台（CMP），该平台使应用开发者能够委托收集和管理与其应用内的第三方SDK数据实践相关的用户同意。标准化举措，例如 IAB 制定的透明度和同意框架 (TCF) [11]，已被引入以指导和标准化 CMP实现。使用遵循行业标准的既定 CMP 通常有望增强隐私合规性和问责制。
然而，对网站 [12]、[13]、[14]、[15]、[16]、[17]、[18] 使用的 CMP的研究表明，它们可以通过多种方式导致无效的用户同意，例如通过在 cookie 横幅中使用预先选择的选项。近年来，移动应用越来越多地采用 CMP，采用率从前 100 名 Android 应用中的 6.6% [8] 上升到本研究中的 8.5%，每个应用的平均下载量为 3860 万次。值得注意的是，排名前 100 的应用往往拥有更大的用户群，采用 CMP的可能性比排名 100 到 200 之间的应用高出 41.7%。这种趋势提出了一个关键问题：采用 CMP，尤其是经过认证符合行业标准的成熟应用，是否能够通过确保移动应用中的有效用户同意来真正确保隐私合规性？回答这个问题并不简单，因为移动 CMP 与网络 CMP 有很大不同。例如，移动 CMP 通常会针对大量多样化的 SDK 提供更详细的隐私披露和更细粒度的请求同意，并且通常涉及更复杂的图形用户界面 (GUI)。相比之下，网站 CMP 通常专注于少数广泛的 Cookie 类别。这些差异限制了基于网络的 CMP 研究结果应用于移动应用的程度。目前，行业领导者通常认为使用已建立的 CMP 可确保隐私合规性，正如他们的官方建议 [19]、[20] 中所反映的那样。然而，在移动应用背景下系统评估这一假设的实证研究仍然明显有限。分析移动应用的 CMP界面。本研究通过调查 Android 和 iOS 这两个领先平台的移动应用中使用 CMP的潜在问题来填补研究空白。
为了实现这一目标，我们首先通过结合 CMP中有效同意的关键标准，为 CMP的隐私可问责设计、实施和使用制定了一套基本规则，称为 DIU规则。然后，我们开发了一个名为 DIULENS 的新高效框架，用于识别 CMP界面 中潜在的违反这些规则的行为（称为 DIU风险）。 DIULENS 基于 GUI 分析方法，通过引入一系列有针对性的设计来解决 CMP界面 发现和 DIU风险分析中的挑战，从而推进当前的研究。具体来说，与应用提供的同意对话框通常结构简单且易于探索不同，CMP界面 往往更加复杂，需要不同的用户交互才能完成探索和分析。例如，遵守 TCF 政策的 CMP 通常采用分层 GUI 结构，跨多个互连的 GUI 显示不同级别的信息（例如，整体个人数据使用情况、SDK 和目的的详细列表），并允许不同粒度的同意选择（例如，接受针对特定 SDK 或目的的全部或逐项同意）。为了应对这一挑战，我们设计了几种专为 CMP 量身定制的新的 LLM 引导的 GUI 分析技术，包括用于区分 CMP界面 与应用中其他 GUI 的 CMP指南感知方法、优先考虑通向 CMP的导航流的 LLM 引导路径探索，以及对 CMP 内的 GUI 进行稳健和全面探索的策略。另一个挑战来自这样的事实：尽管存在 CMP的高级指南，但 CMP界面 的实际外观因不同 CMP 和应用而异，因此无法直接查明 DIU风险（如之前的研究 [8]、[10] 中所做的那样）。
为了克服这一挑战，我们采用了 LLM 推理规则，允许基于 CMP界面 和应用中第三方SDK的实际使用来推理违规行为，从而实现有效且通用的 DIU风险检测，同时捕获其表现形式的变化。
### 真实移动应用中的DIU风险
我们的评估证实了 DIULENS 在发现 CMP界面 方面的效率及其在分析 DIU风险方面的有效性。为了了解现实世界中的 DIU风险，我们收集了两组流行的移动应用，包括 9,332 个 Android 应用和 3,496 个 iOS 应用。在这些应用上运行 DIULENS，我们发现 397 个应用（其中集成CMP的应用占 60.5%，包括 371 个 Android 应用和 26 个 iOS 应用）至少有一项违反 DIU规则的行为。分析这些应用揭示了新的发现和证据，表明即使集成了 CMP，与用户同意相关的问题仍然存在，这是由于对隐私不负责任的 CMP实现及其在应用中的使用和配置。例如，集成CMP的移动应用中有 41.9% 未能提供有关第三方SDK的可信披露信息，例如请求用户同意比应用实际使用的 SDK数量更多或更少，或者在 CMP界面 中显示不一致的 SDK 披露信息，这主要是由于应用开发者未能正确配置 CMP。此外，14.9% 的移动应用要么在提供同意后不允许用户访问 CMP界面，从而难以撤回用户同意，要么强制用户提供同意。具体来说，关于强制同意，我们发现有证据表明应用开发者操纵 CMP配置，使非必要的 SDK（例如分析）看起来对应用功能来说是严格必需的，从而绕过了用户同意。我们还发现一些最受欢迎的 CMP（例如 OneTrust）未能正确提交用户同意选择，这会导致强制用户同意。
此外，8.1% 的集成CMP的应用在显示 CMP界面 之前收集用户个人数据以请求用户同意，并且由于应用开发者在配置 CMP 方面的不良做法以及 CMP实现的固有局限性，11.7% 的应用包含 GUI 元素或导航路径，导致对用户同意产生模糊影响。最后，我们观察到，与 Android 相比，iOS 应用采用 CMP的比例较小，这主要是由于 Apple 的应用跟踪透明度 (ATT) 框架，这凸显了需要更好地集成CMP 和 ATT，以确保符合平台级（即 Apple）要求和更广泛的隐私法规。有趣的是，我们发现据报告存在 DIU风险的 iOS 应用比例较小，因为它们对 CMP的使用通常涉及简化的 CMP界面，例如根据 ICC 类别 [21] 显示 SDK，而不完全支持符合 TCF 的 GUI。我们正在向受影响的利益相关者（应用开发者和 CMP）披露 DIU风险，其中一些风险已经得到确认或解决。为了支持未来移动平台上 CMP 研究，我们在 GitHub 上发布了 DIULENS 的源代码以及 SDK、CMP 和移动应用的数据集 [22]。
### 主要贡献
本文的贡献包括：
**移动应用CMP界面分析的新技术**
我们开发了一个新的 CMP界面 分析框架，称为 DIULENS，具有针对性的设计，可以高效、有效地发现和分析 CMP界面。
**对移动应用DIU风险的新认识**
通过在现实世界的应用上运行 DIULENS，本研究强调了通过 CMP界面 获取用户同意相关的各种问题，解决了关于 CMP的采用是否确保移动应用隐私合规性的知识差距，并进一步为 CMP的隐私可问责设计、实施和使用提供信息。
