# PINFINDER 阅读前置知识

> [!info] 使用方法
> 每次只完成一个单元。先读例子，再合上笔记回答检查题。这里不教真实 Android 工具，只建立读懂论文所需的最小模型。

## 单元一：谁在调用谁

本节只引入三个词：宿主应用、SDK、Wrapper。

### 1. 宿主应用（Host App）

- **白话解释：** 用户真正下载安装和打开的 App。
- **技术含义：** 集成其他组件、提供界面并决定何时调用它们的主程序。
- **在案例中：** 儿童游戏就是宿主应用，它接收用户的年龄与同意选择。
- **为什么需要：** 它离用户最近，必须把用户选择转成后续组件能够理解的设置。
- **只需记住：** 宿主应用负责发起调用，但不一定直接控制所有下游行为。

### 2. 软件开发工具包（Software Development Kit，SDK）

- **白话解释：** 别人写好的功能组件，开发者接入后不用从零实现广告、统计或登录。
- **技术含义：** 提供代码、配置和开发文档的可复用软件包。
- **在案例中：** AdSDK 负责展示广告，并可能访问一个模拟广告标识符。
- **为什么需要：** 隐私风险可能来自第三方组件，而不只来自宿主应用自己的代码。
- **只需记住：** SDK 带来功能，也带来宿主应用需要管理的数据行为。

### 3. 中介组件（Wrapper）

- **白话解释：** 宿主应用和多个下游 SDK 之间的转接层。
- **技术含义：** 用统一入口包装其他组件，并把配置继续传递下去。
- **在案例中：** 游戏只通知 Wrapper“用户拒绝”，Wrapper 再通知 AdSDK。
- **为什么需要：** Wrapper 如果漏传或错传，宿主应用做对了也可能无法影响下游。
- **只需记住：** Wrapper 的关键责任是完整、正确地传递设置。

```text
正确：用户拒绝 → Host App → Wrapper → AdSDK收到拒绝
错误：用户拒绝 → Host App → Wrapper ─X→ AdSDK仍按默认设置运行
```

### 最少记忆清单

1. Host App 是用户安装的主程序。
2. SDK 是被复用的功能组件。
3. Wrapper 是配置和调用的中转层。

### 主动回忆题

1. 用户选择发生在 Host App，为什么 AdSDK 可能不知道？
选择可能没有传递到AdSDK，比如Wrapper拦截了
**与其说 Wrapper“拦截”，更准确是没有转发、错误转换或转发时机不对。**
2. Wrapper 自己停止收集数据，为什么仍可能不够？
可能直接调用SDK的接口上传了数据
**Wrapper 停止自己的行为，不代表它配置了下游 AdSDK；下游 SDK 可能独立访问或上传数据。**
3. 出现数据行为时，责任为什么不能只看最外层 App？
可能是在调用的过程中Wrapper和SDK自己收集数据
**还可补充：问题可能来自 App 配置、Wrapper 传播或 SDK 实现**

## 单元二：文档与代码分别告诉我们什么

本节只引入三个词：隐私指南、隐私相关 API、Android 库文件。

### 1. SDK 隐私指南（Privacy Guidance）

- **白话解释：** SDK 厂商写给开发者的隐私设置说明书。
- **技术含义：** 描述什么条件下要设置什么值，以及设置后厂商承诺改变什么行为。
- **在案例中：** 指南可能写“儿童用户必须先开启限制模式，再初始化广告组件”。
- **为什么需要：** 分析器必须先知道“正确做法”，才能判断实际集成是否偏离。
- **只需记住：** 指南提供规范性期望，不直接证明代码已经照做。

### 2. 隐私相关应用程序接口（Privacy-Sensitive API，PSAPI）

- **白话解释：** 会改变 SDK 隐私设置或数据行为的代码入口。
- **技术含义：** PINFINDER 关注的 SDK 方法；论文将影响隐私合规的 SDK API 称为 PSAPI。
- **在案例中：** `setConsent(false)` 表示把用户拒绝传给 AdSDK。
- **为什么需要：** 报告只有定位到具体入口，才能告诉开发者漏了什么或哪里用错。
- **只需记住：** 普通功能方法不一定是 PSAPI；方法必须和隐私条件或行为有关。

### 3. Android 库文件（JAR/AAR）

- **白话解释：** 开发者拿到的已打包组件代码。
- **技术含义：** JAR 主要包含编译后的 Java 类；AAR 还可包含 Android 资源与配置。
- **在案例中：** 文档只写 `setConsent`，库文件能提供所属类、参数类型等精确身份。
- **为什么需要：** 自动分析不能只靠模糊名称，需要把文档中的说法和代码中的方法对应起来。
- **只需记住：** 文档告诉我们“应该怎样”，库文件帮助确认“代码里到底有什么”。

### 最少记忆清单

1. 隐私指南是正确使用的来源之一，不是运行证据。
2. PSAPI 是影响隐私设置或行为的 SDK 方法。
3. JAR/AAR 用来确认方法在代码中的精确身份。

### 主动回忆题

1. 为什么只搜索方法名可能匹配错方法？
方法名不一定是真正调用隐私相关的接口
**同名方法可能存在于不同类，也可能有不同参数版本；需要完整类名、方法名和参数类型。**
2. 隐私指南遗漏参数值时，分析结果会受什么影响？
可能匹配错方法？
不是主要导致匹配错方法，而是不知道 `true/false` 等参数分别表示什么，从而无法判断调用是否正确。
3. 库文件里存在 `setConsent`，能否证明 App 调用过它？
不能，只能证明方法存在；需要动态运行记录才能证明本次路径确实调用，并确认参数和时间。

## 单元三：三种证据不能互相替代

本节只引入三个词：静态证据、动态证据、人工复核。

### 1. 静态证据（Static Evidence）

- **白话解释：** 不运行程序，直接检查代码里可能存在什么。
- **在案例中：** 找到 Host App、Wrapper 和 AdSDK 之间的调用关系。
- **能证明：** 某个方法、参数或调用路径存在。
- **不能证明：** 用户实际操作时这条路径一定执行过。

### 2. 动态证据（Dynamic Evidence）

- **白话解释：** 运行程序时记录真正发生的事件。
- **在案例中：** 记录用户拒绝、设置调用以及之后的数据访问时间。
- **能证明：** 当前设备、环境和操作路径下观察到了什么。
- **不能证明：** 没观察到的行为在其他路径或环境中永远不会发生。

### 3. 人工复核（Human Review）

- **白话解释：** 人回到原始文档、代码和事件，判断工具的解释是否成立。
- **在案例中：** 确认 `false` 的确表示拒绝，并核对报告引用了正确事件。
- **能证明：** 候选结论经过了有标准的检查。
- **不能证明：** 少量抽样能够覆盖全部未发现问题。

| 问题 | 主要证据 |
|---|---|
| 代码里有没有这个设置方法？ | 静态证据 |
| 本次运行有没有调用？ | 动态证据 |
| 参数含义和报告解释是否正确？ | 文档证据 + 人工复核 |
| 是否找到了所有可能问题？ | 以上证据通常都不足以单独保证 |

### 最少记忆清单

1. 静态证据覆盖可能性，动态证据记录一次实际执行。
2. 没观察到不等于永远不存在。
3. Agent 的解释必须能回到原始证据。

### 主动回忆题

1. 静态分析找到调用，为什么仍需要运行事件？
可能有的方法是动态加载的
**“动态加载”是另一个静态分析局限。这里需要动态证据，是因为静态调用路径不一定实际执行。**
2. 动态分析没有看到数据访问，为什么不能直接判定安全？
这个不知道
**不能；可能是测试路径、地域、年龄、账号、操作时间或观察窗口没有触发。**
3. 人工复核应该核对哪三类原始材料？
应该核对
