## 第一步：论文到底想解决什么

继续使用同一个案例：儿童游戏通过 Wrapper 接入 AdSDK。用户已经选择拒绝个性化广告，但下游组件仍可能不知道、收到错误值，或收到拒绝后继续访问模拟标识符。

以往只看最终网络行为，可以发现“仍然发送了数据”，却不一定能告诉开发者：

- 应该调用哪个 SDK 设置；
- 设置是否在正确时间调用；
- 问题发生在 Host App、Wrapper 还是 AdSDK。

PINFINDER 的核心想法是：把 SDK 方法表达的隐私含义，与本次运行的真实上下文放在一起比较。论文把这类 SDK 集成造成的隐私不一致称为 PIN；这里先把 PIN 理解为“需要人工确认的 SDK 集成问题候选”，不是法律判决。

### 最少记忆清单

1. 目标不仅是发现行为，还要给出可定位到 SDK 方法的修复线索。
2. “方法声称什么”和“上下文实际发生什么”必须一起看。
3. 检测结果是候选问题，需要人工确认。

### 主动回忆题

1. 只知道“发送了标识符”，为什么可能无法直接修复？
2. 哪三层组件都可能造成设置失效？
3. 为什么报告不能直接叫“违法证明”？

- [ ] 能不用 PIN、SDK 等缩写复述研究问题。

## 第二步：先把“应该怎样”写成结构

本节只引入三个字段：正确使用条件、触发条件、预期行为。

PINFINDER 把隐私指南中分散的文字整理成一份 API 隐私描述（API Privacy Description）。对案例中的 `setConsent(false)`，可以简化为：

```json
{
  "api": "AdSDK.setConsent",
  "correct_use": "必须在AdSDK初始化前调用，参数应来自真实用户选择",
  "trigger": "用户已经作出同意或拒绝选择",
  "expected_behavior": "参数为false后不得访问模拟广告标识符"
}
```

- **正确使用条件：** 已经调用时，顺序和参数怎样才算正确。
- **触发条件：** 出现什么上下文时，这个方法必须被调用。
- **预期行为：** 调用之后，组件承诺发生或停止什么。

Agent 可以从文档中提取候选字段，但人需要检查原文是否真的支持这些解释，尤其是 `true/false`、年龄范围和调用顺序。

### 最少记忆清单

1. 正确使用检查“调用得对不对”。
2. 触发条件检查“该调用时有没有调用”。
3. 预期行为检查“调用后的承诺有没有兑现”。

### 主动回忆题

1. “用户拒绝后必须设置 false”同时涉及哪两个字段？
2. 为什么参数含义不能只让 Agent 猜？
3. 文档里的承诺为什么还需要运行事件验证？

### 进入下一节的检查点

- [ ] 能为另一个假想设置写出三个字段。
- [ ] 能指出哪一个字段需要用户事件，哪一个需要后续数据事件。

## 第三步：把“实际发生”排成时间线

本节只引入隐私上下文轨迹（Privacy-Context Trace，PCTrace）和两种上下文分组。

PCTrace 是一条按时间排序的证据记录。先不要背论文的五个符号，只分成两组：

1. **条件上下文：** App 作出的承诺、运行地域/年龄、用户点击了什么。
2. **执行上下文：** SDK 方法怎样调用、之后访问或发送了什么数据。

案例轨迹：

```text
09:00  环境：当前用户是儿童
09:01  用户：点击“拒绝个性化广告”
09:02  调用：Wrapper.setConsent(false)
09:03  调用：AdSDK.initialize()
09:04  数据：AdSDK访问模拟广告标识符
```

论文进一步把上下文细分为五类：App 承诺 `Capp`、运行环境 `Cenv`、用户交互 `Cuser`、SDK 调用 `Capi`、数据行为 `Cdata`。这些符号只是在告诉分析器每条证据属于什么，不是五种新工具。

### 最少记忆清单

1. PCTrace 是按时间排序的证据，不是模型写的自然语言总结。
2. 条件上下文说明规则为什么适用。
3. 执行上下文说明实际调用和数据行为。

### 主动回忆题

1. 如果没有用户点击事件，能否确认 `false` 来自真实选择？
2. 为什么调用和初始化的先后顺序重要？
3. `Cdata` 没有事件时，应该输出安全还是证据不足？

### 进入下一节的检查点

- [ ] 能把五条案例事件按条件/执行分组。
- [ ] 能解释为什么 PCTrace 必须保留时间。

## 第四步：用三条规则提出问题

本节只引入三条规则，不增加工具名。

| 规则 | 白话问题 | 案例中的检查 |
|---|---|---|
| Correct-Use | 已经调用的方法，用法对吗？ | 值是否来自用户拒绝？是否早于初始化？ |
| Triggering | 条件已经满足，必须的方法出现了吗？ | 用户已选择拒绝，AdSDK 是否收到对应设置？ |
| Behavior | 设置之后，承诺兑现了吗？ | `false` 之后是否仍访问模拟标识符？ |

同一条轨迹可能同时触发多条报告。例如 Wrapper 收到了拒绝，但没有继续调用 AdSDK：Wrapper 的调用本身可能正确，AdSDK 层却违反 Triggering；如果 AdSDK 收到拒绝仍访问数据，则检查 Behavior。

### 最少记忆清单

1. Correct-Use：用了，但可能用错。
2. Triggering：该用，但可能没用。
3. Behavior：设置了，但实际行为可能没变。

### 主动回忆题

1. `setConsent(true)` 与用户拒绝冲突，主要是哪条规则？
2. 儿童环境要求调用限制方法但没有调用，主要是哪条规则？
3. `false` 后继续访问数据，主要是哪条规则？

### 进入下一节的检查点

- [ ] 能在不看表格时复述三条规则。
- [ ] 能为每条规则各造一个不同例子。
- [ ] 知道证据不足时应输出 UNKNOWN，而不是猜测。

## 第五步：原论文完整系统做了什么

现在再看原论文流程，不需要第一次掌握所有实现工具：

```text
隐私指南 + SDK代码包
  → 整理“应该怎样”的API隐私描述

App承诺 + 环境 + 用户操作 + SDK调用 + 数据行为
  → 建立“实际发生”的PCTrace

API隐私描述 + PCTrace
  → 检查Correct-Use、Triggering、Behavior
  → 生成候选报告并人工复核
```

论文使用代码分析、自动界面探索、运行时记录、网络观察和大语言模型来扩大规模。第一轮学习只需理解每类工具提供哪种证据；具体工具放到 Android 进阶阶段。

## 来源事实

- 论文将 API 隐私含义建模为正确使用条件、触发条件和预期行为。
- PCTrace 组合 App 承诺、运行环境、用户交互、SDK 调用和数据行为。
- 三类一致性规则用于检查错误使用、遗漏调用和无效行为。

## 我的理解

PINFINDER 最值得学习的不是工具清单，而是先把规范写成可检查条件，再把不同来源的事实组织成一条能回溯的证据链。
