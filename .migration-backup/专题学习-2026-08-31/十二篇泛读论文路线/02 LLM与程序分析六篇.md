# LLM与程序分析六篇

贯穿问题：**LLM 如何参与程序分析，却不让模型的一句话取代工具证据？**

## 单元七：BINREX——让 Agent 调用二进制分析工具

论文卡：[[论文库/2026-BINREX-智能体静态二进制分析]]

- **一句话**：先用大规模函数语义检索帮助理解未知函数，再把任务分层，生成 IDAPython 交给 IDA 执行，最后用谓词检查结果。
- **只学三个词**：Binary（没有源码的编译程序）、Semantic Retrieval（按功能含义检索相似函数）、Verifiable Reasoning（结论能回到地址、引用、调用图等证据）。
- **重点读**：语义检索→分层规划→脚本执行→验证失败重试的循环。
- **记一个结果**：知识检索覆盖约5,700万函数；72项任务中报告83.3%成功率。它不是任意漏洞准确率。
- **连接精读**：与 ScenGen 都是“模型决策、工具执行、监督验证”；与 HScope 都要求可检查的调用/数据关系。
- **边界**：检索结果、任务拆分和验证谓词都可能不完整；能执行脚本不等于结论正确。

### 20分钟动作

把“查找认证绕过”拆成三个子任务，每个子任务写一个可由 IDA 输出验证的完成条件。

### 最少记忆清单

- BINREX 不让 LLM 直接猜二进制答案，而是让工具执行。
- 可验证仍依赖验证条件设计是否完整。

### 主动回忆题

1. 语义检索为什么能帮助 `sub_xxx` 这类未知函数？
2. 地址和调用图证据仍不能消除什么误判？

### 进入下一节检查点

- [ ] 能画出检索、规划、执行、验证四步循环。
- [ ] 能解释83.3%的任务口径。

## 单元八：PANGOLIN——LLM理解接口，Fuzzer提供崩溃证据

论文卡：[[论文库/2026-PANGOLIN-LLM驱动IoT固件模糊测试]]

- **一句话**：用 LLM 恢复多语言 IoT 固件中的接口和参数语义，再由反馈驱动模糊测试生成输入并验证漏洞。
- **只学三个词**：Firmware（设备固件）、Fuzzing（持续输入变异数据寻找异常）、Harness（把目标函数接到模糊测试器的适配代码）。
- **重点读**：跨语言 API 分发、参数规格恢复、Fuzzer 反馈循环，以及 LLM 输出如何被执行证据约束。
- **记一个结果**：在12台、8个厂商设备上发现68个此前未知漏洞，其中31个获得漏洞编号；数量为基线 LABRADOR 的2.96倍。
- **连接精读**：可借鉴到移动 SDK：LLM 提取接口语义，确定性测试器负责触发和保存崩溃；但研究对象不是移动隐私。
- **边界**：硬件、固件版本和接口环境决定复现难度；发现数量不能直接外推到其他厂商。

### 20分钟动作

写一张“LLM 输出/API 规格→Harness→输入变异→崩溃→人工确认”箭头图，并标出真正的漏洞证据从哪一步出现。

### 最少记忆清单

- LLM 帮助恢复测试入口，Fuzzer 负责反馈驱动执行。
- 崩溃也需要去重、定位和人工确认。

### 主动回忆题

1. 为什么仅让 LLM 阅读固件不能替代模糊测试？
2. 多语言接口给 Harness 构造带来什么困难？

### 进入下一节检查点

- [ ] 能区分模型推断和崩溃证据。
- [ ] 能解释2.96倍是在特定基线和设备上的比较。

## 单元九：LLMxCPG——先用程序图裁剪，再让 LLM 判断

论文卡：[[论文库/2025-LLMxCPG-CPG引导漏洞检测]]

- **一句话**：用代码属性图选择与漏洞有关的控制流和数据依赖切片，减少无关代码后再交给 LLM 检测。
- **只学三个词**：CPG（Code Property Graph，代码属性图，把语法、控制流、数据依赖放进同一图）、Slice（程序切片，与目标变量/调用有关的代码子集）、Data Dependency（数据依赖，一个值如何影响另一个值）。
- **重点读**：怎样选择切片种子、怎样遍历图、裁剪后保留了什么上下文。
- **记一个结果**：输入代码规模减少67.84%–90.93%；论文报告相对基线 F1 提升15%–40%，必须结合数据集与基线解释。
- **连接精读**：HScope 计算数据流本身；LLMxCPG 用程序图为 LLM 准备更相关的上下文。
- **边界**：图构建或种子遗漏会把关键代码裁掉；更少 token 不自动等于更可靠。

### 20分钟动作

对一个十行登录函数圈出 Source、条件判断和 Sink，只把相关五行交给“模型”，再说明被删行是否真的无关。

### 最少记忆清单

- CPG 是结构化程序上下文，不只是文本摘要。
- 裁剪提高效率，也可能造成信息丢失。

### 主动回忆题

1. CPG 比纯字符串检索多保留了什么？
2. 切片种子选错会造成误报还是漏报？

### 进入下一节检查点

- [ ] 能手画一个三节点数据依赖图。
- [ ] 能说明代码减少比例与准确率不是同一个指标。

## 单元十：IRIS——让 LLM补规格，让 CodeQL找路径

论文卡：[[论文库/2025-IRIS-LLM辅助静态漏洞分析]]

- **一句话**：LLM 根据漏洞类型生成 Source/Sink 规格并筛选候选，CodeQL 负责跨仓库静态污点分析和路径证据。
- **只学三个词**：Specification（分析规格，告诉工具哪些 API 是 Source/Sink）、CodeQL（把代码转成可查询数据库的静态分析平台）、Candidate Path（等待进一步判断的候选路径）。
- **重点读**：规格生成、CodeQL 路径计算、候选过滤三部分如何交替；特别看 LLM 错误如何被工具证据限制。
- **记一个结果**：初始数据集含120个经人工验证的 Java 漏洞；CodeQL 单独发现27个，IRIS+GPT-4发现55个，并报告6个此前未知漏洞。
- **连接精读**：HScope 的 Source/Sink 多由领域专家设置；IRIS 探索让 LLM 辅助扩展规格。PINFINDER 的 SDK API 知识库也可借鉴这一思路。
- **边界**：LLM 生成的错误规格会扩大误报或漏掉路径；静态候选仍需人工验证。

### 20分钟动作

为儿童游戏案例写三行规格：`getOAID=Source`、`http.post=Sink`、`sanitize=Sanitizer?`，并说明第三行为什么需要验证。

### 最少记忆清单

- LLM 生成“分析需要知道什么”，CodeQL 计算“代码中有哪些路径”。
- 55/120是特定数据集上的发现数，不是55%的通用准确率。

### 主动回忆题

1. IRIS 为什么不是 LLM-only 漏洞检测？
2. 错误 Source/Sink 规格分别会带来什么后果？

### 进入下一节检查点

- [ ] 能区分规格、查询和候选路径。
- [ ] 能解释27与55的比较条件。

## 单元十一：LLM4Decompile——把二进制恢复成更像源码的表示

论文卡：[[论文库/2024-LLM4Decompile-大模型反编译]]

- **一句话**：训练模型直接从低级代码恢复高级代码，或改写 Ghidra 的反编译输出，提高可读性和语义恢复能力。
- **只学三个词**：Decompilation（反编译，从二进制恢复高级表示）、Ghidra（常用逆向工程工具）、Refinement（改写已有反编译结果，而非从零生成）。
- **重点读**：End-to-End 与 Refinement 两条路线；评估到底比较语法相似、可编译性还是功能语义。
- **记一个结果**：论文卡记录 Refinement 路线相对 End 模型进一步提升16.2%；汇报前要回正文确认具体指标名称与测试条件。
- **连接精读**：它可以为 BINREX 等二进制 Agent 提供更可读输入，但本身不负责漏洞或隐私结论。
- **边界**：看起来像源码不代表语义等价；编译器优化会丢失变量名和高级结构。

### 20分钟动作

找一个五行 C 函数和对应反编译伪代码，标出丢失的变量名、类型和控制结构；不要尝试大型恶意程序。

### 最少记忆清单

- 反编译解决表示恢复，不自动解决安全判断。
- 可读性、可编译性和语义等价是不同指标。

### 主动回忆题

1. 为什么反编译结果“读起来正确”仍可能功能错误？
2. Refinement 相比从零生成利用了什么先验？

### 进入下一节检查点

- [ ] 能说出两条模型路线。
- [ ] 汇报时不会把16.2%省略为无口径的“准确率提升”。

## 单元十二：BugAuditor——从正确代码反推项目规则

论文卡：[[论文库/2026-BugAuditor-不一致防御代码审计]]

- **一句话**：从项目中大量一致的资源释放、检查或初始化代码归纳隐含规则，再寻找少数缺失防御的敏感操作。
- **只学三个词**：Defensive Code（防御代码，如检查、释放、清理）、Project-specific Oracle（项目特定判错标准）、Inconsistency（相似上下文中的实现不一致）。
- **重点读**：防御操作种子→程序分析提取上下文→分组→LLM 归纳模式→审计不一致→人工确认。
- **记一个结果**：发现54个长期缺陷，20个已确认修复，2个获 CVE；LLM-only 在这54个中的召回很低，显示关键是结构化模式和程序证据。
- **连接精读**：可迁移到 PINFINDER：若多数 SDK 接入点都先检查 consent，少数没检查可作为候选；但“少数不同”不自动等于 bug。
- **边界**：多数代码也可能共同犯错，合法例外也会形成不一致；必须检查控制流和语义。

### 20分钟动作

写10个小函数：8个 `open→close`、1个漏 `close`、1个把资源交给调用者释放；比较字符串规则和人工语义判断。

### 最少记忆清单

- 项目现有正确实践可以成为未写下来的规范。
- 不一致只是候选，合法例外必须保留。

### 主动回忆题

1. 为什么多数写法不一定正确？
2. 怎样把“先检查 consent”变成可检查项目模式？

### 进入下一节检查点

- [ ] 能解释项目特定 Oracle 的价值。
- [ ] 能指出至少一个合法不一致例子。
