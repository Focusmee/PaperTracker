# 移动隐私与供应链六篇

贯穿问题：**用户看到的隐私承诺，怎样才能与 App、第三方库和真实数据行为对应起来？**

## 单元一：MATE——审计移动智能体的完整轨迹

论文卡：[[论文库/2026-MATE-移动智能体策略感知安全审计]]

- **一句话**：把任务指令、Agent 操作轨迹和自然语言安全策略一起输入轻量模型，判断轨迹是否违反策略。
- **只学三个词**：Trajectory（轨迹，连续动作记录）、Security Policy（安全策略，允许/禁止规则）、Policy-conditioned Audit（策略条件化审计，同一行为按不同策略判断）。
- **重点读**：项目页图1；知识生成→合成训练数据→模型训练→真实日志审计；再看 In/Out/Real 三类评估。
- **记一个结果**：知识覆盖158个 App、形成14万余条训练轨迹；MATE-3B 在162条真实轨迹上的准确率为95.06%，不能外推为任意 App 的漏洞检出率。
- **连接精读**：ScenGen 产生 GUI 轨迹，MATE 审计轨迹是否越过策略；DIULENS 则检查 CMP 和同意风险。
- **边界**：它看日志而非 APK 数据流，漏记的 SDK/网络事件无法被审计。

Mobile Agent 可以在真实手机上执行点击、输入、转账和发消息等高风险操作，而同一条操作轨迹在不同用户或 APP 的安全策略下可能有不同的安全结论，因此作者提出了 policy-aware trajectory auditing。

最大难点是缺少大量真实的危险 Agent trajectory，所以作者没有直接大规模操作真实 APP，而是从 158 个 APP 的功能说明、操作流程和安全政策中构建知识库，再利用 LLM 合成 Instruction、Trajectory 和 Policy-conditioned Annotation，并通过结构检查、语义修复和人工验证得到超过 14 万条训练数据。

随后作者通过 trajectory-policy mismatch、multi-policy 和 multi-app 三种增强方式训练 Qwen2.5 0.5B～3B 模型，使模型根据 **Instruction + Trajectory + Security Policy** 输出 **Violation、Risk Category 和 Rationale**。

在部署时，再利用 Trajectory Adapter 把截图/XML 等不同 Agent 日志转换成统一的 ReAct trajectory，并用 Policy Retriever 从策略库中自动找相关政策，最后交给 MATE 审计。

- **只学三个词**：Third-party Library（第三方库）、Responsibility Boundary（责任边界）、Triangulation（三角验证，用访谈、文档和代码互相验证）。

## 单元三：Android AR Privacy——AR数据访问与披露是否一致

论文卡：[[论文库/2026-AndroidARPrivacy-安卓AR数据访问隐私风险]]

- **一句话**：用领域知识、静态调用分析和 Frida 动态确认，检查 Android AR App 的敏感数据访问、披露和最小权限。
- **只学三个词**：ARCore/ARFoundation（两类 AR 开发框架）、Disclosure（数据披露）、Least Privilege（最小权限，只访问功能真正需要的数据）。
- **重点读**：完整分析链路图、领域规则怎样建立、静态候选如何进入动态确认。
- **记一个结果**：179个 App；静态发现58个未披露访问实例，其中23个动态确认；82个最小权限候选中40个动态确认。
- **连接精读**：像 HScope 一样追踪调用关系，像 DIULENS 一样比较承诺与行为，像 PINFINDER 一样依赖 SDK/API 知识。
- **边界**：只覆盖特定 AR 框架；动态确认仍受执行路径限制。

### 20分钟动作

把“58→23、82→40”画成两层漏斗，并分别标注静态候选和动态确认。

### 最少记忆清单

- 静态候选数量不能直接当成已确认问题。
- AR 框架知识是分析能否正确归因的前提。

### 主动回忆题

1. 为什么动态确认数通常低于静态候选数？
2. “未披露访问”和“最小权限违规”有什么区别？

### 进入下一节检查点

- [ ] 能准确解释四个数字的分母和阶段。
- [ ] 能说出框架覆盖范围带来的外推限制。

## 单元四：Plain Text, Plain Risks——WebView明文风险

论文卡：[[论文库/2026-PlainTextPlainRisks-AndroidWebView明文风险]]

- **一句话**：先静态筛选可能允许明文的 WebView App，再用自动化触发和定制 WebView Provider 记录真实 HTTP 行为并归因第三方库。
- **只学三个词**：WebView（App 内嵌浏览器）、Mixed Content（HTTPS页面加载HTTP子资源）、Provider（提供 WebView 内核能力的系统组件）。
- **重点读**：图1和方法链；为什么静态筛选后只对高风险候选动态测试；怎样按 FQCN 归因宿主或第三方库。
- **记一个结果**：静态分析189,779个 App；动态测试35,000个高风险候选；2,790个在实验中真实产生 HTTP 流量。
- **连接精读**：给 DIULENS/PINFINDER 提供“静态候选→动态事实→责任归因”的大规模流水线范例。
- **边界**：允许明文只是候选；Monkey 没探索到的路径仍可能漏掉。

### 20分钟动作

画三层证据：允许HTTP配置→运行时HTTP请求→可利用影响，并说明每层需要什么工具。

### 最少记忆清单

- 配置、真实请求和可利用漏洞是三个证据层级。
- 定制 Provider 是统一监控点，不等于逐个 App 手工插桩。

### 主动回忆题

1. 为什么 `usesCleartextTraffic=true` 不能直接判漏洞？
2. 35,000 为什么不是全部189,779个 App？

## 单元五：Bridges to Self——网页怎样通过 localhost 找到原生 App

论文卡：[[论文库/2026-BridgesToSelf-移动端localhost静默追踪]]

- **一句话**：网页脚本曾通过手机 localhost 与原生 App 通信，把网页 Cookie 与长期 App 身份关联，并可能在 Cookie 同意前发生。
- **只学三个词**：localhost（设备自身网络地址）、Web-to-App Bridge（网页到原生 App 的本机通信桥）、Deterministic Tracking（用明确ID一一关联的追踪）。
- **重点读**：图1、威胁模型、§4 多源测量和同意实验。
- **记一个结果**：研究覆盖 Top-100K 网站和5,000个热门 Android App；披露后相关厂商于2025-06-03停止该机制。
- **连接精读**：把 DIULENS 从“CMP→SDK”扩展到“网页→localhost→App/SDK”，提醒同意前副作用可能发生在跨上下文通道。
- **边界**：localhost 也有合法用途，必须结合标识、时间和厂商证据；历史机制已停止，不能说今天仍然存在。

### 20分钟动作

画出 Web ID、localhost 端口、App ID 和 consent=false 的时间线。

### 最少记忆清单

- localhost 不是自动安全边界，也不是自动恶意证据。
- 历史发现必须注明披露和停止时间。

### 主动回忆题

1. 为什么清 Cookie 后仍可能被重新识别？
2. 怎样区分合法本机通信和跨上下文追踪？

## 单元六：Health Hazard——健康数据承诺与真实外传

论文卡：[[论文库/2026-HealthHazard-HealthConnect隐私风险]]

- **一句话**：向 Health Connect 写入可识别的合成健康数据，再用 API Hook、调用栈和网络流量检查 App 的访问、分享与公开声明是否一致。
- **只学三个词**：Health Connect（Android健康数据仓库）、Priming（先注入已知示踪值）、Stack Trace（显示调用来源的函数链）。
- **重点读**：图2、动态分析管线、网络外传和局限。
- **记一个结果**：最终351个 App；60.9%未遵守UI透明指南，25.6%未报告相关收集/分享，69个（19.6%）把数据发往网络。
- **连接精读**：和 DIULENS 都对比“用户看到的承诺”与运行行为；可用 ScenGen 改善人工操作瓶颈。
- **边界**：论文把数据离开设备称为 leak，不自动等于法律违法；动态结果仍是覆盖下界。

### 20分钟动作

用三种颜色标出“权限/声明”“API读取”“网络发送”，并写出哪种证据由谁产生。

### 最少记忆清单

- 合成健康数据是示踪剂，便于在网络中匹配。
- UI、API与网络证据必须分开记录。

### 主动回忆题

1. 有读取权限是否等于允许上传？
2. 为什么人工操作限制了测量规模？
