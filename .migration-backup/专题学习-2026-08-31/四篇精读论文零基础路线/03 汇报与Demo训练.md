# 汇报与 Demo 训练

## 你的汇报主线

不要按“论文 A 讲完再讲论文 B”堆四份摘要。用一个问题贯穿：

> 用户在儿童游戏里拒绝个性化广告后，我们怎样证明这个选择从界面一路传到 SDK，并真正影响数据行为？

四篇论文回答四个相邻问题：API 是否正确、数据可能流到哪里、如何自动完成场景、如何汇总成隐私风险。

## 15分钟、10页幻灯片结构

| 页 | 时间 | 讲什么 | 必须出现的证据 |
|---|---:|---|---|
| 1 | 0:40 | 标题与贯穿案例 | 一张角色链路图 |
| 2 | 1:10 | 背景：App、Wrapper、SDK、CMP | 用户选择传播链 |
| 3 | 1:20 | 共同难题：只看界面或代码都不够 | 静态/动态/LLM边界表 |
| 4 | 1:30 | PINFINDER | 三类规则 + 一条错误调用 |
| 5 | 1:30 | HScope | Source-to-Sink 路径图 |
| 6 | 1:30 | ScenGen | 五类 Agent 闭环 |
| 7 | 2:00 | DIULENS | 系统流程 + 四条 DIU 规则 |
| 8 | 1:40 | 四篇对比与统一证据链 | [[02 四篇论文方法对比]] 的整合图 |
| 9 | 1:40 | 最小 Demo | 输入、三类证据和规则结果 |
| 10 | 1:00 | 局限、启发和研究问题 | UNKNOWN、人工复核、下一步 |

留约 1 分钟处理现场停顿。不要在每页塞论文所有实验数字，每篇只保留能支撑观点的 1–2 个数字。

## 3分钟口头版

1. **30秒背景**：一款 App 的隐私选择要跨宿主、Wrapper 和第三方 SDK，界面上点了拒绝不代表底层已执行。
2. **90秒方法**：PINFINDER 查 API 使用，HScope 查静态数据流，ScenGen 自动完成 GUI 场景，DIULENS 用四条规则组合多源证据。
3. **40秒 Demo**：展示一次“拒绝”路径、一个错误 API 参数、一条 Source-to-Sink 候选和最终 `RISK/UNKNOWN`。
4. **20秒结论**：LLM 负责语义和探索，确定性工具与人工负责证据和确认。

## 最小联合 Demo：只实现思想，不冒充论文复现

### Demo 边界

- 使用本地合成 App 和合成 SDK，不测试真实用户数据。
- HScope 部分用简化语言/JSON 表示数据流，不解析真实 Ark 字节码。
- PINFINDER 部分复用 [[项目/PINFINDER-Python模拟/00 项目主页]]。
- ScenGen 部分只做三页场景和动作后验证。
- DIULENS 部分复用已有规则与证据分层，参考 [[00 学习地图]]。

### 演示链路

```text
1. 启动合成 App
2. Agent/Appium 找到“设置→隐私→拒绝个性化”
3. 保存截图、控件、动作、前后状态为 trace.json
4. 静态模拟器发现 Wrapper 调用 setPersonalizedAds(true)
5. 污点模拟器给出 OAID → payload → network 的候选路径
6. 规则器输出 DIU-4=RISK，其他证据不足项输出 UNKNOWN
7. 点击证据编号，展示对应截图、调用点和路径
```

### 每一阶段谁做什么

| 阶段 | 目的 | 输入 | 你来做 | Agent/程序做 | 输出 | 掌握标准 |
|---|---|---|---|---|---|---|
| 合成 App | 提供可控实验对象 | 三页需求 | 写页面和状态变量 | 构建并启动 | APK/本地页面 | 可手动完成拒绝 |
| GUI 探索 | 复现用户路径 | 场景、截图/UI树 | 定义成功条件 | 选择并执行动作 | `trace.json`、截图 | 每步都有前后状态 |
| API 检查 | 观察错误配置 | 调用事件 | 预测规则结果 | 匹配参数/顺序 | API 风险记录 | 能解释三类规则 |
| 数据流检查 | 观察静态候选 | 简化语句 | 定义 Source/Sink | 传播污点 | 路径证据 | 能逐步复述传播 |
| DIU 汇总 | 形成规则结论 | 三类证据 | 决定证据门槛 | 输出判定 | PASS/RISK/UNKNOWN | 每个结论能回链 |

## 建议证据数据结构

```json
{
  "case_id": "child_game_reject_ads",
  "ui_trace": [{"action": "tap_reject", "before": "cmp.png", "after": "saved.png"}],
  "api_event": {"signature": "AdSdk.setPersonalizedAds(boolean)", "value": true},
  "dataflow": ["getOAID", "wrap", "http.post"],
  "rule_result": {"DIU-4": "RISK", "evidence": ["ui_trace[0]", "api_event"]}
}
```

课堂上先展示错误版本 `value=true`，再改成 `false` 重新运行。这样观众能看到证据变化如何影响规则，而不是只看静态截图。

## 老师可能追问的问题

### 1. 四篇为什么能放在一起？

它们共享同一个证据链，但研究问题不同：PINFINDER 检查隐私 API 责任，HScope 追踪代码数据流，ScenGen 生成动态场景轨迹，DIULENS 组合证据检查同意管理风险。

### 2. LLM 是否直接判断违规？

不应如此。LLM 用于理解界面语义和推荐探索动作；事实要落在截图、程序路径、参数、状态变化和运行事件上，高影响结论再人工核验。

### 3. 静态路径与动态事件冲突怎么办？

不强行二选一。静态路径说明可能性，动态事件只覆盖本次运行。检查动态覆盖是否触发了该路径；无法排除时保留 UNKNOWN 或风险候选。

### 4. 这个 Demo 是论文复现吗？

不是完整复现，而是教学型方法验证。它复现四种核心思想，但没有达到论文的数据规模、平台分析、真实 SDK 知识库和完整评估条件。

### 5. 最大研究机会是什么？

把 GUI Agent 的可重放轨迹、SDK API 规则和静态数据流统一成带证据引用的合规分析，并系统评估自动化结论与人工 Ground Truth 的一致性。

## 最少记忆清单

- 汇报用一个案例串四篇，不堆四份摘要。
- Demo 必须明确是教学原型，不声称完整复现。
- 结论必须区分 PASS、RISK 和 UNKNOWN，并能回到证据。
- 最重要的局限是覆盖范围、框架/SDK 知识完整性和人工确认成本。

## 主动回忆题

1. 如果只能演示三份证据，你会选哪三份，为什么？
2. 怎样证明 Agent 不是碰巧点对了一次？
3. Demo 中哪一部分最像 HScope，哪一部分只是简化替代？
4. 什么条件满足后，你才会把“候选风险”升级为“人工确认”？
5. 如果老师质疑四篇研究对象的平台不同，你如何回应？
