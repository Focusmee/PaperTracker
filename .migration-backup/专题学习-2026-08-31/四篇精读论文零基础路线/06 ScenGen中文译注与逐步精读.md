# ScenGen 中文译注与逐步精读

> [!warning] 版本说明

## 论文信息

- 英文题目：*Scenario-Guided LLM-based Mobile App GUI Testing*
- 中文学习题目：场景引导的基于 LLM 的移动 App GUI 测试
- 作者：Shengcheng Yu 等八人
- 出处：ACM TOSEM，ASE 2026 Journal First
- 一句话：让五类 Agent 围绕完整业务场景循环观察、决策、执行、监督和记录，最后产生可复核、可回放的测试脚本。

## 先用人话看懂整篇论文

> [!summary] 30 秒版本
> ScenGen 是一个“会看手机界面、会规划操作、会检查自己有没有点错”的自动化测试系统。测试人员只告诉它“登录账号”或“把商品加入购物车”这样的目标，系统就尝试自己完成整套操作，并把成功过程保存为可以检查和重放的测试脚本。

### 它解决什么问题

传统自动化测试工具擅长到处点击、增加页面或代码覆盖率，却不保证真的完成一项有业务意义的任务。例如，要测试“购买商品”，随机工具可能点过搜索框、菜单、广告和返回按钮，但始终没有完成“搜索商品—选择商品—加入购物车”。

ScenGen 关注的问题是：**能否围绕一个真实用户目标，自动生成一条逻辑连贯、可以执行、可以验证、可以重放的操作路径？**

这里的测试场景不是预先写死的逐步脚本，而是一个高层目标，例如：

- 登录账号；
- 创建并保存笔记；
- 查询北京天气；
- 搜索鞋子并加入购物车。

### 现有方法为什么不够

1. **随机或覆盖率驱动的方法没有目的感**：可能访问很多页面，但没有走完目标业务流程。
2. **预建状态图、规则或场景图的方法比较僵硬**：遇到广告、弹窗、隐藏菜单、异步加载或新版界面时，已有模型容易失效。
3. **直接让一个 LLM 连续操作不稳定**：模型可能忘记历史、重复点击、虚构控件或者提前宣布任务完成。
4. **LLM 知道点什么，却不擅长给出精确坐标**：语义理解正确不代表真正点中目标。
5. **执行后若没有验证，错误会沿着长流程累积**：页面可能仍在加载、实际没有点中，或者进入了错误页面。

### 它提出了什么方法

可以把 ScenGen 想象成一个由五种角色组成的测试小组：

- **Observer**：看懂页面上有哪些候选控件，给控件画框并编号。
- **Decider**：结合目标、当前页面和历史动作决定下一步做什么，并选择目标控件。
- **Executor**：把决定翻译为确定性的设备命令并执行。
- **Supervisor**：检查页面是否加载完成、动作效果是否正确、整个场景是否完成。
- **Recorder**：保存动作、坐标、截图、命令和日志，最终生成可重放脚本。

五种角色通过 Context Memory 共享当前截图、历史截图、控件集合、历史动作、场景和 App 信息。完整闭环是：

```text
观察界面 → 决定下一步 → 定位控件 → 执行操作
    ↑                              ↓
更新记忆 ← 保存证据 ← 验证结果 ←─┘
```

### 作者具体做了什么

> [!info] 来源事实
> 作者实现了多角色移动 GUI 测试框架；组合计算机视觉、OCR 与多模态 LLM 识别和理解控件；将逻辑决策与控件定位拆成两个阶段；设计控件预测、位置调整和失败自纠正；加入加载、状态转移和场景完成三级验证；通过 ADB 操作 Android App；把轨迹序列化为 JSON；监控日志发现崩溃；最后在 92 个 App、99 个 App—场景任务和 10 类场景上进行评估。

### 论文正式列出的三项贡献

1. 提出场景引导的 LLM 移动 GUI 测试框架，把高层测试意图与底层可执行操作连接起来。
2. 提出面向测试的控件定位增强机制，通过 Widget Prediction、Location Adjustment 和纠错提高定位可靠性。
3. 构建包含十类代表性场景的评估基准，并通过实证实验验证场景生成和 Bug 暴露能力。

### 最后效果怎么样

- 99 个任务中的场景覆盖率为 **86.87%**，正常完成且完整覆盖的成功率为 **84.85%**。
- 系统报告 **106 个场景相关 Bug**；原文说明这些主要是运行日志或异常退出暴露的崩溃，并经人工确认，其中 **83.02%** 得到开发者验证或修复。
- 逻辑决策按表 5 的汇总计数由 **96.08%** 提高到 **97.06%**。
- 控件定位经纠正后达到约 **98%**。
- 平均每个场景生成时间约 **4.71 分钟**，平均 API 费用约 **0.32 美元**。

> [!warning] 数字使用提醒
> 原文在控件定位准确率和决策准确率的汇总行、正文叙述之间存在小数差异。课堂上可说“定位最终约 98%，决策最终约 97%”，并以表格计数为准，不要把冲突的小数当作精确结论。

### 这个结果不代表什么

ScenGen 证明的是“系统能较稳定地走完目标 GUI 场景并保存证据”，不是“系统已经证明 App 功能完全正确”。Supervisor 是场景一致性检查器，不是传统的精确测试判定器；RQ2 中的 Bug 也主要是崩溃，不应扩大解释为所有功能错误、安全漏洞或隐私违法。

## 第一单元：摘要与引言——为什么“点得多”不等于“测得对”

### 原文摘要译读

传统移动 GUI 测试通常追求事件多样性、代码覆盖或状态空间探索，却不保证生成动作符合 App 的业务逻辑。因此测试可能产生互不相关的点击、在完整流程结束前停止，或漏掉只有在多步语义依赖后才出现的失败。

ScenGen 将“测试场景”作为自动化的一等单位。系统使用五类专职 Agent 和共享上下文记忆形成闭环：Observer 理解当前界面，Decider 根据目标选择动作，Executor 进行确定性设备操作，Supervisor 验证状态转移与场景完成，Recorder 保存状态、动作、命令和运行信息。成功过程被序列化为可回放 JSON，之后可以不再调用 LLM。

### 引言译读

LLM 让测试工具能够理解自然语言目标，但直接让模型看截图并输出坐标存在认知—执行鸿沟：语义可能正确，坐标却点错；单次动作成功也不代表整个场景完成；一步错误若不检查会在长流程中持续累积。论文因此把不确定推理与确定性执行分开，并在每一步加入监督和纠正。

### 三个新术语

- **Testing Scenario（测试场景）**：具有完整业务目标和先后逻辑的用户任务。
- **Cognition-execution Gap（认知—执行鸿沟）**：模型理解“点搜索框”但无法准确映射到可点击位置。
- **Closed Loop（闭环）**：动作后重新观察和验证，再决定下一步。

### 最少记忆清单

- 页面覆盖率不能代表完整场景完成。
- LLM 语义决策与设备执行必须分离。
- 每一步都需要后置状态验证。

### 主动回忆题

1.  [^1]Monkey 点遍许多页面，为什么仍可能没有完成“拒绝广告”场景？
因为 **“页面覆盖多” ≠ “业务场景完成”**。

Monkey 的目标更接近“尽量多点、多探索状态”，它可能确实进入过：

> 设置页 → 隐私页 → 广告页 → 其他页面……

但“拒绝广告”实际上是一个有**先后依赖和终止条件**的场景，例如：

**进入设置 → 找到隐私设置 → 找到个性化广告 → 关闭开关 → 保存 → 确认设置已经生效**

Monkey 可能每个页面都访问过，却没有按照正确顺序把这些动作串起来。比如它刚进入隐私页，又随机点了返回；甚至点过“拒绝”按钮，但没有点击“保存”。所以覆盖了页面，不代表完成了完整任务。文件中也特别强调：传统工具可能访问很多页面，但没有走完目标业务流程。

可以记成：

**Monkey关心：我去过多少地方？**  
**ScenGen关心：我有没有把这件事办完？**

2. 模型选择正确按钮文字但点击失败，错在认知还是执行？
主要属于**执行/定位层错误，而不是认知错误**。

假设模型已经判断：

> 下一步应该点击“拒绝个性化广告”。

说明它在**语义认知上是正确的**——它知道“要干什么”。

但是如果它输出的坐标偏了，比如文字“拒绝个性化广告”在 `(500, 800)` 附近，真正可点击的是旁边的开关，而它却点到了文字、空白处或者另一个控件，那么问题发生在：

**语义目标 → 实际 GUI 坐标**

这个映射阶段，也就是论文所说的 **Cognition-execution Gap（认知—执行鸿沟）**：模型理解“点哪个”，不代表能够准确点中。

所以可以这样区分：

**选错了按钮 → 认知/决策错。**

**按钮选对了，但没点中 → 定位/执行错。**

这也是 ScenGen 为什么把“逻辑决策”和“控件定位”拆开：这样才能知道错误到底来自“想错了”，还是“点错了”。

3. 为什么长任务中一次错误会越来越严重？
因为长任务里的步骤通常具有**前置依赖关系**。

例如正确路径是：

**设置 → 隐私 → 广告设置 → 关闭个性化广告 → 保存**

假设第 2 步本来应该点击“隐私”，结果误点成“账户”。

如果系统**不检查这一步是否成功**，下一轮模型可能仍然认为：

> “我已经进入隐私页面了。”

于是继续寻找“个性化广告”。

但实际上它现在在账户页面。

接下来就可能发生：

**第一次错误：进入错误页面**  
↓  
**错误状态被当成正确状态写入历史**  
↓  
**后面的决策基于错误前提**  
↓  
**找不到目标 → 猜控件 → 再点错**  
↓  
**越来越偏离原始目标**

所以一次小错误会变成一连串错误，这就是**错误累积**。论文明确指出，如果执行后不验证，错误会沿长流程持续累积。

ScenGen 的解决办法就是每一步都做：

**执行 → 重新观察 → 验证状态 → 再决定下一步**

而不是：

**执行 → 默认成功 → 继续执行**

这就是所谓的 **Closed Loop（闭环）**。

你可以把这三题最后压缩成三句话记：

> **1. 点得多 ≠ 任务做完，场景要求动作有业务逻辑和终止条件。**  
> **2. 想对了但没点中，是认知—执行鸿沟中的定位/执行错误。**  
> **3. 长任务步骤相互依赖，如果错误状态不及时验证纠正，后续决策就会建立在错误前提上，导致误差不断累积。**

## 第二单元：第2节——三种真实 GUI 困难

### 背景译读

场景由多个逻辑相关动作组成。每个动作不仅依赖当前截图，也依赖先前已完成步骤和最终目标。论文用三类例子说明困难：重要功能可能藏在菜单或上下文图标里；正确操作可能需要领域知识；复杂功能需要多步输入、等待和选择。

### 动机例子译读

隐藏功能例子说明仅按显眼控件探索会错过目标。计算器例子说明即使 GUI 很简单，没有运算语义也无法判断结果。购物例子说明“搜索—选择商品—配置规格—加入购物车”中的每一步都为下一步建立前置条件。随机动作即使单步合法，组合后也可能没有业务意义。

### 三个新术语

- **Precondition（前置条件）**：执行某动作前必须满足的状态，例如先进入设置页才能看到隐私选项。
- **Business Logic（业务逻辑）**：动作之间的语义和顺序关系。
- **Long-horizon Task（长程任务）**：需要许多相互依赖步骤才能完成的目标。

### 最少记忆清单

- 控件可见不等于业务上此刻应该点击。
- 场景需要前置条件、动作和完成条件。
- 长流程需要记忆和纠错。

### 主动回忆题

1. “关闭个性化广告”的前三个前置条件是什么？
打开 App → 进入设置 → 进入隐私设置 → 才能关闭个性化广告
2. 随机点击为什么可能每一步都合法但整体无意义？
因为“这个按钮现在能不能点”与“这个按钮是不是当前任务应该点的”是两回事。

比如购物任务是：

> 搜索商品 → 选择商品 → 选规格 → 加入购物车

随机工具可能做的是：

> 点搜索框 ✅  
> 点返回 ✅  
> 点菜单 ✅  
> 点广告 ✅  
> 再点个人中心 ✅

这些动作单独看都没有问题，App 也都允许执行，所以每一步都算“合法”。

但它们之间没有形成完成目标所需要的**业务逻辑和顺序关系**。

所以：

**单步合法 ≠ 整体有意义**

ScenGen 强调的是：

> 当前动作不仅要“能执行”，还要服务于最终场景目标，并满足动作之间的前置依赖。

可以类比成你要去学校：

> 出门 ✅ → 去超市 ✅ → 去健身房 ✅ → 去公园 ✅

每一步都合法，但最后没到学校。

3. 领域知识在计算器与隐私设置中分别是什么？
计算器需要数学领域知识；隐私设置需要理解隐私选项的语义、顺序和操作效果。

## 第三单元：第3.1节——上下文记忆让 Agent 不会失忆

![[附件/论文截图/ScenGen-图3-多智能体框架.png]]

> [!note] 图3看图顺序
> 从左到右读五类 Agent，再看下方 Context Memory 如何向每轮提供当前截图、历史截图、历史动作、场景与 App 信息。反馈箭头表示动作失败后会重新观察和决策。

### 原文译读

LLM 本身不会永久记住多轮 GUI 状态。ScenGen 建立分层上下文记忆：长期记忆保存设备、系统、App 和场景等稳定信息；工作记忆保存当前目标、已执行动作和 Agent 交互；短期记忆保存最近截图、候选控件与识别结果。这样 Decider 能知道自己处在流程哪一步，并避免反复点击同一控件。

记忆不是把所有截图无限塞进提示词。系统区分稳定信息与最近状态，以控制上下文长度，并让 Recorder 把每次结果写回共享存储。

### 三个新术语

- **Long-term Memory（长期记忆）**：设备、App、场景等稳定信息。
- **Working Memory（工作记忆）**：当前目标、动作历史和执行进度。
- **Short-term Memory（短期记忆）**：最近 GUI 截图、控件和识别结果。

### 最少记忆清单

- 三类记忆按信息稳定性与时间范围分层。
- 记忆支持一致决策，也控制重复探索。
- Recorder 负责把动作结果写回记忆。

2. “刚才点击隐私按钮失败”应放哪类？
3. 为什么不能把全部历史原样放进每次提示？

## 第四单元：第3.2—3.4节——观察、决策、执行和记录

### Observer 译读

**Observer 组合计算机视觉、OCR 和多模态 LLM。CV 产生确定性控件边界，OCR 提取文字，LLM 解释控件语义。候选控件被画框并编号，模型只需要选择编号而不是直接生成像素坐标。系统还合并重复识别结果、过滤噪声和非交互元素。**


**PS：CV/OCR主要是为了把视觉定位结构化、提高定位可靠性；工程上也会间接减少无效 LLM 调用和 token 消耗，但不能把“省 token”说成论文里 CV/OCR 的唯一或主要目的。**


### Decider 译读

Decider 分两阶段。逻辑决策先根据场景、当前 GUI 和历史动作选择动作类型、意图、目标描述和输入内容；目标定位再把语义目标映射到候选控件。若识别遗漏，Widget Prediction 根据附近空间关系估计虚拟目标；若文字标签不可点击，Localization Adjustment 把位置移到相邻输入框或开关。

### Executor 与 Recorder 译读
jia
Executor 把选择转换为 ADB 点击、输入、滑动、返回或等待命令，严格执行而不重新解释目标。Recorder 保存意图、动作、目标、坐标、命令、前后截图与日志，最后构造可回放 JSON 脚本。

### 三个新术语

- **Visual Grounding（视觉定位）**：把语义目标映射到界面坐标。
- **Widget Prediction（控件预测）**：检测器漏掉控件时，根据相邻结构估计目标区域。
- **Replayable Script（可回放脚本）**：保存精确命令和状态，使后续测试无需 LLM。

### 批注：职责分离为什么可靠

Observer 负责“有什么”，Decider 负责“做什么”，Executor 负责“确实做了”，Recorder 负责“留下了什么”。若一次 LLM 同时包办四件事，错误来源就难以定位，也难以重放。

### 最少记忆清单

- 先做语义决策，再做位置映射。
- Executor 是确定性工具，不应自由修改计划。
- 成功轨迹要保存成无需 LLM 的脚本。

## 第五单元：第3.5节——Supervisor 如何阻止错误累积

### 原文译读

Supervisor 在动作执行后做三类验证。自适应加载验证判断页面是否仍在加载，避免固定等待过短或过长；状态转移验证判断动作是否产生与意图一致的变化；场景完成验证判断所有目标是否已经满足。

若状态没有推进，系统区分定位错误、缺少前置步骤和逻辑决策错误，并把反馈交回对应上下文。必要时执行回滚，再重新决策。Supervisor 的判断仍可能使用多模态 LLM，因此它不是绝对可靠的测试 Oracle；截图、控件变化和运行日志仍需保存。

### 三个新术语

- **State-transition Verification（状态转移验证）**：比较动作前后状态是否符合意图。
- **Test Oracle（测试判定器）**：决定实际结果是否符合预期的机制。
- **Rollback（回滚）**：偏离目标后返回已知状态并重新规划。

### 批注：状态变化不等于成功

广告轮播、电量图标或时间更新都会改变像素。可靠验证要检查与目标相关的语义控件和文本，例如点击“隐私设置”后是否出现“个性化广告”，而不是只比较截图差异。

### 最少记忆清单

- Supervisor 检查加载、状态转移和场景完成。
- 失败反馈必须指出错误类型。
- 监督器也会误判，不能取消证据保存和人工核验。

## 第七单元：第5—8节——威胁、讨论与结论

### 有效性威胁译读

App 和场景样本有限；人工判断可能带主观性；模型版本、提示和温度会影响结果；动态页面、登录、验证码、付费和系统弹窗会造成不可控状态。这些因素限制结果推广。

### 讨论译读

论文讨论模型可替换性、长程任务的上下文窗口限制、多阶段推理与效率的权衡，以及 ScenGen 与通用 GUI Agent 的差别。更多 Agent 不自动带来可靠性；价值来自明确责任、共享记忆、验证反馈与可回放证据。

### 结论译读

ScenGen 证明场景可作为 GUI 测试的核心组织单位。通过多 Agent 分工与闭环纠错，工具可以更稳定地完成具有业务逻辑的长流程，并把成功过程转化为传统测试可复用的脚本。

### 三个新术语

- **Threat to Validity（有效性威胁）**：可能让实验结论偏离真实情况的因素。
- **Model Substitutability（模型可替换性）**：系统更换底层 LLM 后是否仍保持能力。
- **Reproducibility（可重复性）**：其他人能否用相同材料得到相近结果。

- 多 Agent 的价值是可分责、可验证、可纠错。
- 动态 GUI 测试仍受环境与路径覆盖限制。
- ScenGen 可替 DIULENS 走路径，不能替 DIULENS 判合规。

## 第九单元：这个系统在程序里如何实现

### 先纠正一个容易产生的误解

ScenGen 的“五个 Agent”不等于五个大模型同时在群聊。更准确的理解是：**一个控制器按固定顺序调用五类软件模块，其中 Observer、Decider 和 Supervisor 会调用多模态 LLM，Executor 和 Recorder 主要是普通确定性代码。**

因此它的本质是一个带状态、带工具调用、带反馈的循环程序。

### 1. 输入和运行环境

系统启动时需要：

- 一段高层场景描述，例如“搜索鞋子并加入购物车”；
- 待测 App 和包名；
- 已连接的 Android 真机或模拟器；
- 屏幕分辨率、系统版本等设备信息；
- 可选的起始页面、输入值或参考截图。

这些稳定信息进入长期记忆。程序随后通过 **ADB（Android Debug Bridge，安卓调试桥）** 启动 App、截图并执行点击、输入、滑动和返回。

### 2. Observer 如何从截图得到控件

一次观察可以拆成以下代码步骤：

```text
screenshot = adb_screencap()
cv_boxes   = detect_by_edges_and_contours(screenshot)
text_boxes = run_ocr(screenshot)
widgets    = merge_and_filter(cv_boxes, text_boxes)
annotated  = draw_id_for_each_widget(screenshot, widgets)
semantics  = multimodal_llm_interpret(screenshot, annotated, widgets)
```

论文使用 UIED 风格的计算机视觉流程，通过边缘检测、轮廓分析和组件分组找候选区域；OCR 负责文字；规则代码根据距离阈值合并相邻文字、图标和标签，并删除重复框、状态栏、过大区域和过小噪声。

最终输出的控件记录可以抽象为：

```json
{
  "id": 44,
  "text": "Kids",
  "bbox": [120, 640, 330, 720],
  "description": "shopping category entry"
}
```

标注截图的作用是让 LLM 选择 `44`，而不是自己猜 `(225, 680)` 这样的坐标。

### 3. Decider 为什么要分成两次推理

第一次是逻辑决策，只回答下一步要做什么：

```json
{
  "intent": "进入儿童鞋分类",
  "action_type": "click",
  "target_description": "Kids"
}
```

它的提示输入包括目标场景、当前截图和历史动作。第二次才把 `Kids` 与当前控件集合匹配，得到控件 ID 和坐标。这样可以分别判断：

- 逻辑是否错了，例如本应搜索却决定返回；
- 定位是否错了，例如目标是对的但匹配到另一个相似按钮。

若没有匹配目标，程序请求模型预测相对位置；若找到的是标签，程序再调整到相邻的输入框或开关。输出必须符合固定 JSON 结构，不能直接执行任意自然语言。

### 4. Executor 怎样保证动作可控

Executor 只接受有限动作类型，例如：

```text
click  → adb shell input tap x y
input  → 先点击输入框，再 adb shell input text ...
swipe  → adb shell input swipe x1 y1 x2 y2 duration
back   → adb shell input keyevent 4
wait   → 控制器等待后重新截图
```

它不重新解释测试目标，也不允许 LLM 直接拼接并执行任意系统命令。这样即使模型推理不稳定，设备操作层仍然是受约束和可复现的。

### 5. Supervisor 如何形成闭环

动作执行后，Supervisor 不是只问一次“成功了吗”，而是分三步：

```text
if 页面仍在加载:
    继续等待并重新截图

if 当前状态不符合刚才动作的预期:
    判断是没有变化、点错控件还是进入错误页面
    必要时返回上一个有效状态
    把失败原因发回 Decider

if 当前状态已经满足整个场景目标:
    结束测试
else:
    开始下一轮观察和决策
```

状态检查使用动作前后截图、标注控件、最新动作和场景目标。对于短暂弹窗或动画，系统会在一个观察窗口内连续截取多张图片。若只出现时钟、广告轮播等无关变化，应判为没有产生与目标相关的有效状态转移。

### 6. Recorder 和 Context Memory 保存什么

Recorder 每轮写入：

- 动作意图与动作类型；
- 目标控件文字、编号和边界框；
- 输入内容或滑动方向；
- 精确 ADB 命令；
- 操作前后截图；
- 验证结果和失败反馈；
- 运行日志中的异常或崩溃。

Context Memory 可以用数据库、JSON 文件或进程内对象实现，关键不是使用哪种存储技术，而是分清三类内容：稳定的 App/设备信息、当前任务历史、最近一轮 GUI 状态。程序还可用感知哈希和结构相似度判断两个页面是否基本相同，从而减少循环和重复探索。

[^2]PS：Memory 很大，但 Context Window 有限，所以要按照信息价值来分配
#### 第一优先级：当前状态

```
当前截图
当前控件
当前页面文字
```

因为这是决定下一步最重要的。

---

#### 第二优先级：任务目标

```
目标：关闭个性化广告
```

永远不能丢。

否则模型容易跑偏。

---

#### 第三优先级：最近几步历史

例如：

```
刚才：
进入 Settings
点击 Privacy 失败一次
```

防止重复。

---

#### 第四优先级：历史摘要

例如不要发：

```

step3...
...
step40...
```

而是：

```

未完成：

```

### 7. 成功轨迹怎样变成可重放脚本

场景完成后，Recorder 把累计动作序列序列化为 JSON：

```json
{
  "scenario": "搜索鞋子并加入购物车",
  "device_width": 1080,
  "device_height": 1920,
  "actions": [
    {
      "intent": "打开分类",
      "action_type": "click",
      "target_widget": {"id": 44, "text": "Kids"},
      "command": "adb shell input tap 225 680"
    }
  ]
}
```

探索阶段需要 LLM，重放阶段只读取已保存命令。这样同一条路径可以用于回归测试、Bug 复现和人工审查。

### 8. 主控制循环伪代码

```python
memory = initialize_context(app, device, scenario)

while not memory.finished:
    gui = observer.observe(memory)
    proposal = decider.choose_next_action(gui, memory)
    action = decider.localize_target(proposal, gui.widgets)

    before = gui.screenshot
    executor.execute(action)
    after = observer.capture_current_state()

    verification = supervisor.verify(
        scenario=memory.scenario,
        action=action,
        before=before,
        after=after,
        history=memory.actions,
    )

    recorder.record(action, before, after, verification)
    memory.update(action, after, verification)

    if verification.failed:
        executor.rollback_if_needed()
        decider.receive_feedback(verification.reason)
```

这段伪代码不是论文仓库的逐行源码，而是把论文架构翻译成软件工程控制流，便于理解模块间如何传递数据。

### 9. 如果做一个最小复现，应该按什么顺序

1. 先实现 ADB 截图、点击、输入和返回，证明设备控制稳定。
2. 再用 OCR 与简单 OpenCV 给页面候选控件编号，输出 `widgets.json` 和标注截图。
3. 接入一个多模态 LLM，只让它输出下一步动作和控件编号。
4. 用固定白名单把 JSON 动作转换成 ADB 命令。
5. 加入操作前后截图比较与失败重试。
6. 最后才加入 LLM Supervisor、分层记忆、回滚和场景完成判断。

初学者不要一开始就复刻五类 Agent。先跑通“观察—选择编号—执行—记录”四步，再逐渐加入监督和纠错，最容易理解每个模块到底解决了什么问题。

### 实现部分最少记忆清单

- Agent 是有明确输入输出的软件角色，不等于五个模型并行聊天。
- LLM 做语义推理，CV/OCR 给候选控件，ADB 做确定性执行。
- 每轮必须保存动作前后证据，并根据验证结果继续、纠错或结束。
- LLM 主要用于生成探索轨迹，最终脚本可以脱离 LLM 重放。

## 课堂用一句话

ScenGen 的核心不是“让五个 LLM 一起点手机”，而是把不确定的语义推理、确定性设备执行、动作后验证和可回放记录组织成闭环。

[^1]: **Monkey** 是 Android 里很经典的“随机点手机”测试工具。它会自动生成大量点击、滑动、返回、按键等事件，目的主要是看 App 会不会崩溃、卡死，以及尽量探索更多页面。它不真正理解业务目标，所以可能“到处都点过”，但并没有完成“登录”“关闭个性化广告”“加入购物车”这类完整任务。
	
	例如你让 Monkey 测一个购物 App，它可能是：
	
	> 点首页 → 点广告 → 返回 → 点搜索 → 返回 → 点个人中心 → 乱滑……
	
	它探索了很多界面，但不保证完成：
	
	> 搜索鞋子 → 选择鞋子 → 选择尺码 → 加入购物车。
	
	这正是你这份材料里说的：随机或覆盖率驱动方法可能访问很多页面，却没有走完目标业务流程。

[^2]: 假设你跑一个 100 步任务。
	
	如果每次都把：
	
	```
	第1步截图
	第1步OCR
	第1步动作
	第2步截图
	第2步OCR
	……
	第99步所有信息
	```
	
	全部发送：
	
	token 就会爆炸。
	
	于是可以：
	
	### Long-term
	
	每轮可能只发送一个非常简短版本：
	
	```
	App: xxx
	Scenario: Disable personalized ads
	Device: Android
	```
	
	---
	
	### Working
	
	压缩成：
	
	```
	Completed:
	- Open settings
	- Enter privacy
	
	Failed:
	- Tap label "Ads" once
	```
	
	而不是完整保存所有过去聊天。
	
	---
	
	### Short-term
	
	只发送：
	
	```
	最近1～2张截图
	当前widgets
	最近一步动作
	```
	
	这样 prompt 就很小。
